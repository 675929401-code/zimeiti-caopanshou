## 版本角色

```text
服务器 current
= 当前线上稳定版

Git stable / stable-* tag
= 服务器稳定版保险点

Codex 本地沙箱
= 开发和测试环境

Git main
= 候选新版

云端数据库
= 业务数据主来源
```

## 三端一致与双版本保留规则

日常开发采用“三端一致 + 双版本保留”的主流程：

```text
Git main
= 本地端、Git 仓库、服务器之间的代码同步锚点

本地端
= 从 Git main 拉取最新代码后进行优化、验证和打包

服务器端
= 只部署 Git main 中已经提交并验证过的版本
```

核心原则：

1. 正常闭环完成后，本地端、Git main 和服务器端的“代码版本”应保持一致。
2. 每次开始优化前，先确认本地已从 Git main 拉到最新，并建立“优化前版本”回滚点。
3. 优化完成并本地验证通过后，提交为“优化后版本”并推送到 Git main。
4. 服务器部署时，只从 Git main 拉取“优化后版本”，不直接接收本地临时文件；部署验证通过后，服务器 current 与 Git main 对齐。
5. 下一次优化时，仍然先从 Git main 拉取最新代码到本地，再建立本轮新的优化前回滚点，不能只凭旧本地目录继续改。
6. 任意时刻至少保留两个版本：
   - 优化前版本：本轮开始前的 commit / 回滚点 / 服务器 previous release。
   - 优化后版本：本轮修改完成后的 candidate commit / 部署后 current release。
7. 如果优化后版本上线出问题，优先回到本轮“优化前版本”；不要直接回滚数据库，除非明确确认业务数据损坏并得到用户授权。
8. Git 保存代码版本、补丁、发布清单和灾备快照；云端数据库仍是用户、订单、积分、智能体、对话历史等业务数据的主来源。

三端状态判断：

```text
本地端 = Git main = 服务器 current
说明：代码已经闭环同步，可开始下一轮优化。

本地端 ≠ Git main
说明：本地存在未提交修改或未拉取最新代码，先处理差异再继续。

Git main ≠ 服务器 current
说明：Git 已有新版但服务器尚未部署，不能声称线上已更新。

服务器 current ≠ 本地端
说明：服务器与本地不一致，下一次优化前必须先以 Git main 为锚点重新拉取。
```

注意：`stable-*` tag 仍然只用于“服务器稳定版完整灾备保险点”。普通的日常优化版本通过 Git main 和本地回滚点保存，不得把未经服务器健康检查和数据快照校验的本地候选版标记为 stable。

## 小更新、大更新与变量数据保护规则

### 小更新

用户说“做个小更新”“修一下这个样式/按钮/排序/文案/轻量逻辑”“Git 仓库和服务器同步”时，默认按小更新处理：

```text
本地修复代码
→ 本地必要验证
→ 提交并推送到 Git 仓库 main
→ 服务器同步该 commit
→ 重启/热更新服务
→ 检查首页、关键 API 和本次改动页面
```

小更新只同步代码、样式、静态资源、说明文档和可迁移配置结构；不得覆盖生产业务数据。

### 大更新

只有用户明确说“完整版”“优化后的最新版”“完整覆盖服务器代码”“把完整新版本部署到 Git 仓库并发布到服务器”等口令时，才按大更新处理：

```text
创建本轮回滚点
→ 完整检查本地代码
→ 提交并推送完整候选版到 Git 仓库 main
→ 服务器新 release 目录完整发布
→ 构建验证通过后切换 current
→ 保留 previous release
→ 检查登录、智能体、模型、API、对话历史、订单积分等关键链路
```

大更新覆盖的是代码和可版本化配置结构；默认仍不覆盖云数据库中的业务变量数据。

### 变量数据边界

以下内容属于变量数据/业务数据，默认不由 Git 仓库实时覆盖，也不得在普通部署时被旧文件覆盖：

```text
用户和管理员账号
password_hash 与认证配置
新增智能体、智能体提示词、分类和排序
模型列表、模型启用状态、模型价格、模型健康配置
API Key、第三方服务配置、插件配置
平台主题、导航、公告、弹窗、通知等后台配置
对话历史和消息正文
充值订单、扣费流水、积分余额、会员、试用、邀请
上传文件、头像、封面、视频、音频及对象存储引用
```

这些数据的主来源是云数据库和对象存储；本地 Codex 沙箱与服务器只要连接同一套云数据库，就应看到同一份数据。

### 禁止覆盖项

无论小更新还是大更新，默认禁止：

```text
清空生产数据库
用本地 sqlite/json/mock 数据覆盖云数据库
导入旧快照覆盖当前生产数据
覆盖 .env.local / .env.production 中的生产密钥
覆盖 uploads/storage 这类生产上传资源目录
用仓库里的演示数据重置智能体、模型、订单、积分和聊天记录
```

只有用户明确说“恢复数据库快照”“连数据库也恢复”“生产数据库损坏，需要从保险点恢复”时，才允许进入数据库恢复流程；恢复前必须先备份当前生产数据库。

### Git 快照的用途

Git 仓库可以保存变量数据快照，但它不是实时数据库。变量数据进入 Git 的唯一合规形式是灾备快照：

```text
server-stable/backups/latest.json
server-stable/manifest.json
server-stable/health-check.txt
```

该快照只用于服务器崩盘、数据库不可用或用户明确授权的恢复场景。普通小更新和大更新发布时，只做只读检查，不自动导入快照。

## 完整灾备标准

用户说：

```text
把当前服务器稳定版创建一个保险点。
```

必须备份到 Git 的内容：

```text
server-stable/
  source/                  # 服务器当前运行源码或可恢复源码
  backups/latest.json       # 当前云端数据库完整快照
  manifest.json             # 版本、commit、时间、服务器、目录、PM2 名称
  health-check.txt          # 首页、登录、智能体、聊天记录、API、乱码检查
```

`backups/latest.json` 至少必须包含：

```text
users（管理员、普通用户、手机号、邮箱、角色、状态、password_hash）
agents / bots（智能体、提示词、分类、排序、头像、开关状态）
categories / nav_items（分类与导航配置）
conversations / conversation_messages（对话历史和消息正文）
payment_orders / credit_transactions / user_transactions（充值、扣费、积分流水）
memberships / trial_plans / invitations（会员、试用、邀请相关数据）
site_settings / platform_config / models / plugins（平台设置、模型、插件配置）
notifications / popup_pushes（公告、弹窗、平台通知）
storage_objects 或上传资源清单（头像、封面、附件、对象存储引用）
```

登录密码规则：

```text
不保存明文密码。
必须保存 password_hash 和认证所需配置。
恢复后，管理员和普通用户应能继续使用原密码登录。
```

## 稳定 tag 规则

稳定 tag 命名：

```text
stable-YYYYMMDD-v版本号
```

示例：

```text
stable-20260802-v2.5
```

只有满足下面条件，才允许创建稳定 tag：

```text
源码可恢复
数据库快照完整
用户 password_hash 存在
聊天记录表和消息表存在
订单、积分、会员数据存在
智能体和平台配置存在
中文无乱码
首页、登录、智能体、关键 API 健康检查通过
```

缺少业务数据的备份，只能叫“代码备份”，不能叫“完整灾备”，不得创建 `stable-*` tag。

## 拉取 Git 最新版本

用户说：

```text
拉取 Git 仓库最新版本。
```

默认执行：

```text
从 origin/main 拉取最新候选代码到 Codex 本地。
不连接服务器，不恢复数据库，不部署线上。
```

标准命令：

```powershell
git -c safe.directory="E:/codewenjanjia/AI内容工作台学习版/04_网站项目/自媒体操盘手/当前版本" status --short
git -c safe.directory="E:/codewenjanjia/AI内容工作台学习版/04_网站项目/自媒体操盘手/当前版本" fetch origin --tags
git -c safe.directory="E:/codewenjanjia/AI内容工作台学习版/04_网站项目/自媒体操盘手/当前版本" pull --ff-only origin main
```

如果本地有未提交改动或 `--ff-only` 失败，不强行覆盖；先建立回滚点，再确认处理方式。

## 部署候选新版

用户说：

```text
把 Codex 优化后的新版本推送到 Git，并部署到服务器。
```

执行：

1. 本地检查 diff、status、构建和关键接口。
2. 推送 `main` 作为候选新版。
3. 连接服务器前，读取私有凭据文件。
4. 服务器先备份当前现场。
5. 新目录拉取 `main`，安装依赖并构建。
6. 验证通过后切换 PM2/Nginx/current。
7. 询问是否创建新的 `stable-*` 保险点。

## 灾难恢复

用户说：

```text
恢复到最近一个稳定版本。
```

执行：

1. `git fetch --tags`。
2. 找到最新 `stable-*` tag。
3. 告诉用户将恢复的 tag。
4. 备份当前服务器现场。
5. 从 tag 恢复到服务器新目录。
6. 构建并验证。
7. 服务器崩盘或数据库不可用时，恢复 `backups/latest.json` 完整业务快照。
8. 验证通过后切换线上入口。

灾难恢复验收：

```text
管理员账号可用原密码登录
普通用户账号可用原密码登录
历史聊天记录可见
智能体、订单、积分、会员和平台配置完整
中文显示正常
```

## 禁止事项

1. 禁止把只有源码、没有完整业务快照的备份标记为稳定版。
2. 禁止把只有首页 200 的检查当作登录和数据库恢复成功。
3. 禁止用乱码快照恢复生产数据库。
4. 禁止把 Git 当实时数据库；Git 保存代码状态和灾备快照。
