# 文案提取保护合同

本专项合同落实用户在 2026-10-29 提出的要求：排查文案提取状态跟踪异常，保留正常配置，功能稳定后加安全锁，后续触碰须经用户本人允许。全局规则仍只服从根 AGENTS.md；本合同只定义提取功能的保护范围。

## 保护内容与唯一清单

源码清单为 [.engineering/extraction-feature-lock.v1.json](../.engineering/extraction-feature-lock.v1.json)，逐文件保存 SHA-256；不包含密钥、Cookie、Token、数据库连接串。配置保护的角色集合唯一保存在 [extraction-feature-lock.ts](../src/lib/extraction-feature-lock.ts)。文案、视频、批量、搜索共用三合一插件，因此共享配置一并受保护。

- 后台插件 POST、PUT、DELETE 在任何数据库写入之前拒绝受保护变更，返回 `423 / EXTRACTION_FEATURE_LOCKED`。覆盖新建替代插件、改入或改出角色、修改地址、价格、凭据、启停与删除；超级管理员会话同样不能解除。读取与正常提取不受此写入保护影响。
- 本地构建、发布预检和标准制品构建先执行源码摘要校验，失败时不继续。校验只读，不自动修复或重新生成清单；标准本地入口会在停预览、改版本和构建前拒绝。
- 源码锁同时保护供应商协议、结果解析、原请求状态、计费幂等、历史恢复以及锁和构建入口。当前批准只覆盖本次状态跟踪修复与建锁，不授权今后其他功能顺带触碰。

## 后续获准变更

1. 执行方先校验当前锁并读取实时交接，将拟改文件、配置字段、原因和影响说明给用户。
2. 取得用户本人对本次具体变更的明确指令，再 Begin 并保存可逆差量；禁止把一般任务、其他功能优化或旧批准作为通用解锁。
3. 在批准范围内修改，执行必要回归；若涉及供应商请求，先查询原请求与账务，不能为诊断重复提交。
4. 逐项审查新基线，记录授权来源、验证证据与摘要；只有这次获准变更才能手工更新保护清单，再执行校验和 Complete。没有自动解锁按钮、环境变量旁路或自动刷新基线脚本。

这是配置 API 和标准工程流程的防误改保护。拥有相同文件系统写权限或数据库 service-role 权限的执行方仍可能绕过，因此不宣称操作系统硬锁或数据库触发器锁。当前没有实现绑定用户身份、具体变更摘要并原子消费的在线单次解锁系统；不能以现有管理员登录或二次验证时窗冒充这种授权。

## 原请求状态与恢复边界

前台等候超过 30 秒会转为按原请求编号查询，查询只 GET 状态，不重新提交。短暂读失败会退避重试；结果未知继续查询；切回页面立即刷新；鉴权失效明确要求重新登录。提取历史支持初次读失败恢复和窗口焦点刷新。

管理员“提取对账”是未决对账列表，只列结果未知或长时间未更新的请求，不是所有任务列表。已成功的正文应在该账号的“提取历史”查看。

现有 Coze 提交后由原服务进程查询供应商任务；保存 task ID 不等于有独立耐久 worker。本次没有重写任务队列、没有迁移数据库，也未证明服务重启后仍能自动把未知任务推进到终态。遇到这种情况必须查询原 task ID 和费用，不能换请求编号重发。
