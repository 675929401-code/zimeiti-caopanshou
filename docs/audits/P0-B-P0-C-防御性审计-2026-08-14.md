# P0-B / P0-C 防御性审计报告

- 审计日期：2026-08-14
- 审计方式：源代码只读审计、数据库迁移盘点、现有测试盘点、TypeScript/ESLint 静态检查
- 审计边界：未发起真实支付，未调用付费模型，未执行数据库迁移，未进行外部攻击或破坏性测试，未修改生产代码
- 结论：当前版本不应在完成下述 P0 修复与回归测试前开放真实充值或付费生成

## 1. 执行摘要

本次确认的核心问题不是单个接口报错，而是资金与资源交付缺少统一事务边界：

1. 钱包扣费存在并发漏扣。多个请求可读取同一个旧余额，并把余额覆盖成相同的新值，实际只扣一次却交付多次资源。
2. 余额更新、交易流水、资源任务和收益记录分散写入，任一步失败都可能造成账实不一致。
3. 图片、视频和聊天存在“先调用付费上游，再后扣费”的路径。扣费失败时可能免费发放结果，或平台已经产生成本但用户未被扣费。
4. 支付回调、余额入账与订单置为已支付不是一个数据库事务；退款也没有同步冲正用户余额。
5. 支付幂等依赖描述文本和临时覆盖 `payment_url`，缺少数据库唯一键与正式状态机。
6. 存在已认证用户可触发的 SSRF、对象级越权、服务端模型密钥外送和内部模型渠道信息泄露风险。
7. 现有 `tests` 未覆盖支付、退款、并发扣费、SSRF、BOLA 或公开 API 字段泄露；项目中也未发现对应钱包/支付事务迁移。

## 3. A：按严重级别排序的可复现事实

## P0：上线阻断

### P0-01 并发扣费并非真正 CAS，可漏扣或重复交付

- 文件/函数：
  - `src/lib/billing-executor.ts:103-218`，`executeCreditDeduction`
  - `src/lib/billing-executor.ts:229-365`，`executeCashDeduction`
  - `src/lib/billing.ts:395-514`，`deductCreditsWithAgentBilling`
  - `src/lib/billing.ts:528-639`，`deductCredits`
  - `src/app/api/voice/billing/deduct/route.ts:39-87`
- 事实：余额先读后算；更新条件仅检查 `id` 与 `balance >= amount`，没有比较读取到的旧余额。语音扣费甚至只有 `id` 条件。
- 并发场景：余额 10 元，两个 8 元请求同时读到 10，各自把余额写为 2；两个请求均可能成功，用户只被扣 8 元却获得两次服务。
- 影响：图片、视频、聊天、语音可出现漏扣、免费交付、统计失真。

### P0-02 余额与流水不在同一事务，账实不可审计

- 文件/函数：
  - `src/lib/billing-executor.ts:131-198,258-327`
  - `src/lib/billing.ts:428-511,543-634,765-995`
  - `src/app/api/voice/billing/deduct/route.ts:60-87`
- 事实：先更新余额，再插交易流水；流水错误被记录后继续返回成功。部分统计字段也采用独立“读后写”。
- 故障场景：余额更新成功后数据库连接中断，交易流水插入失败。余额已变，但没有可对账记录；重试又可能再次扣费。
- 影响：无法证明每一分钱对应哪次资源交付，四账对账不能闭合。

### P0-03 图片、视频与聊天先消费上游、后扣费

- 文件/函数：
  - `src/app/api/video/generate/route.ts:421-530`
  - `src/app/api/image/generate/route.ts:808-837`
  - `src/lib/llm-billing.ts:78-174`
  - `src/app/api/llm/handle-stream.ts:58-205,280-303`
- 事实：
  - 同步视频生成后才扣费；扣费失败仍返回视频，`price` 为 0。
  - 图片生成后才扣费；扣费失败虽不发图，但平台已承担上游成本。
  - 流式聊天在内容已经发送后异步扣费；失败只记日志。
  - 非流式聊天也在上游响应后扣费，扣费失败仍可能返回结果。
- 攻击/并发场景：低余额账户并发请求多个昂贵任务，所有请求都通过生成前余额检查并消耗上游资源，结算阶段只有少数甚至没有成功扣费。
- 影响：直接经济损失。

### P0-04 支付入账幂等依赖描述文本，且不是一个事务

- 文件/函数：`src/lib/payment-fulfillment.ts:26-137`
- 事实：
  - 通过交易 `description ILIKE %orderId%` 查重，没有结构化精确引用与唯一索引；订单号中的 `_` 在 SQL LIKE 中还是通配符。
  - 通过把 `payment_url` 临时改写成 `fulfilling:*` 抢占处理权，业务字段被当作锁字段使用。
  - 钱包入账、流水、订单置为 `paid` 分开执行。
  - 钱包函数可在流水写失败时仍返回成功。
- 故障场景：钱包已到账但订单更新前进程崩溃；重试因流水缺失再次入账。反向场景也会形成已支付订单但资金账不完整。
- 影响：重复入账、漏入账、订单状态与余额不一致。

### P0-05 回调金额校验可被非数值绕过，且未绑定订单支付渠道

- 文件/函数：`src/lib/payment-fulfillment.ts:52-80`
- 事实：`Math.abs(Number(paidAmount) - order.amount) >= 0.01` 在 `Number(paidAmount)` 为 `NaN` 时结果为 `false`，校验可意外通过；订单查询未取出并核对 `payment_provider` 与币种。
- 安全场景：签名验证库若对异常字段宽松，或状态查询把本地金额当作平台金额传入，异常金额可能进入履约；不同渠道回调也可能错误履约同一订单。
- 影响：错误金额入账、跨渠道混淆。

### P0-06 退款没有钱包冲正，也没有外部调用幂等状态机

- 文件/函数：`src/app/api/payment/refund/route.ts:36-70`
- 事实：外部退款成功后只把订单改为 `refunded`；没有扣回用户现金/积分、没有退款流水、没有处理余额已消费的策略；并且不区分订单支付渠道，统一调用迅虎退款。
- 重放/崩溃场景：两个管理员请求可同时调用外部退款；外部成功后、订单更新前崩溃，重试再次调用退款。用户已收到退款但站内余额仍可继续消费。
- 影响：双重损失和账务纠纷。

### P0-07 支付状态补偿可把未付款订单误判为已支付

- 文件/函数：`src/app/api/payment/status/route.ts:68-100,123-174,187-249`
- 事实：`detectBalanceChange` 用“订单创建后是否存在同金额正向流水”推断支付成功，未精确关联订单；平台查询固定走迅虎，未按订单渠道分发；查询成功后履约使用本地订单金额而不是平台返回并验证的实付金额/币种。
- 场景：两个相同金额订单、管理员充值或其他同额充值，会使未支付订单被标记为已支付。
- 影响：虚假支付状态、错误入账与发货。

### P0-08 LLM 请求允许客户端决定服务端请求地址，并可能携带服务端密钥

- 文件/函数：`src/app/api/llm/route.ts:53-60,551-556,773-805`
- 事实：请求体可传 `proxyUrl/proxy_url`，初始化为 `agentProxyUrl`；最终 `apiBase = agentProxyUrl || LLM_API_BASE`，而 `useApiKey` 可回退到服务端 `LLM_API_KEY`。
- 场景：在没有可信模型配置覆盖该值的路径中，已认证用户可让服务端向自定义地址发请求，并把服务端 Authorization 凭据发送到该地址。
- 影响：SSRF、模型密钥外泄、内部网络探测、上游费用滥用。
- 处理原则：普通用户只能提交不透明的公开模型 ID，地址、渠道、内部模型 ID 和密钥必须完全由服务端映射。

### P0-09 通用 URL 抓取接口存在 SSRF

- 文件/函数：`src/app/api/fetch-url/route.ts:7-17`
- 事实：只要求登录，未校验协议、解析后的 IP、端口、重定向或响应大小，直接让服务端抓取用户 URL。
- 场景：请求回环地址、私网地址、链路本地地址、云元数据地址或经重定向到上述地址。
- 影响：内部服务访问、凭据获取、端口探测、带宽与内存消耗。

### P0-10 存储“从 URL 上传”存在 SSRF，LocalProvider 存在路径穿越

- 文件/函数：
  - `src/app/api/storage/upload/route.ts:62-68,99-117`
  - `src/storage/object/providers/local.ts:54-82,85-104`
- 事实：用户 URL 直接进入 `uploadFromUrl`；provider 使用普通 `fetch` 并整包读入内存。LocalProvider 把可控文件名/键直接交给 `path.join`，没有 `resolve` 后的根目录包含检查。
- 场景：私网 URL、重定向、超大响应造成内存 DoS；`../` 文件名或 key 逃逸存储根目录。
- 影响：内部数据读取、任意路径写/读/删风险、服务崩溃。

### P0-11 视频轮询接口缺少对象所有权校验

- 文件/函数：`src/app/api/video/poll/route.ts:35-60,160-223`
- 事实：查询、更新任务只按 `taskId`，没有同时限定 `user_id = 当前用户`。
- 场景：用户 A 获知用户 B 的任务 ID 后读取状态/视频 URL，并可触发对该任务的轮询和状态更新；后续扣费逻辑还可能错误作用到当前调用者。
- 影响：视频数据泄露、跨账户状态修改、错误扣费。

### P0-12 会话 ID 可导致对象级越权/所有权覆盖

- 文件/函数：`src/app/api/llm/route.ts:839-875`，以及 `src/app/api/llm/handle-stream.ts:188-197`
- 事实：客户端提供 `conversationId` 后按主键 `upsert`，冲突时可更新 `user_id`，没有先以 `(id,user_id)` 原子确认所有权。
- 场景：用户 A 知道用户 B 的会话 ID，提交同 ID 后可能改写会话归属并写入消息。
- 影响：聊天历史泄露、篡改和归属劫持。

## 4. B：最小可落地修复架构

### 4.1 钱包账本与预授权

建议新增三类数据库实体，所有金额使用整数最小货币单位；积分保持整数：

1. `wallet_accounts`
   - 聚合余额：`cash_available_minor`、`cash_reserved_minor`、`credits_available`、`credits_reserved`。
   - 每用户一行，通过 `SELECT ... FOR UPDATE` 串行修改。
2. `wallet_ledger`
   - 只追加，不更新、不删除。
   - 必填：`user_id`、`asset_type`、`entry_type`、`amount`、`balance_after`、`idempotency_key`、`reference_type`、`reference_id`、`metadata`。
   - `idempotency_key` 全局唯一，或至少 `(user_id,idempotency_key)` 唯一。
3. `wallet_reservations`
   - 状态：`reserved -> settled | released | expired`。
   - 与图片、视频、语音、LLM 请求 ID 一一绑定。

建议数据库 RPC：

- `reserve_wallet_funds(...)`：锁账户、校验余额、移动 available 到 reserved、写账本与 reservation，同事务返回。
- `settle_wallet_reservation(...)`：按实际费用结算，释放差额，唯一幂等。
- `release_wallet_reservation(...)`：失败/取消/超时释放，唯一幂等。
- `apply_wallet_adjustment_atomic(...)`：管理员调整、补偿、债务回收，必须携带幂等键和审计理由。

固定价图片/视频/语音：调用上游前全额 reserve，成功 settle，失败 release。

变价 LLM：按输入 token 与允许的 `max_tokens` 计算最坏成本进行 reserve；余额不足时降低 `max_tokens` 或拒绝。流结束后按真实 usage settle 并释放差额。任何流都不能在 reserve 成功前向用户发送。

### 4.2 支付入账状态机

新增：

- `payment_callbacks`：保存 provider event ID 或规范化 payload hash，唯一索引防重放；敏感字段加密/脱敏。
- `payment_refunds`：`created -> submitting -> submitted -> succeeded | failed | manual_review`。
- `payment_orders` 增加 `currency`、`amount_minor`、`provider_transaction_id`、`fulfillment_version`、`fulfilled_at`，不再复用 `payment_url` 做锁。

RPC `fulfill_payment_order_atomic(...)` 应在同一事务内：

1. 锁定订单。
2. 核对订单状态、渠道、币种、整数实付金额、用户。
3. 插入 callback 幂等记录。
4. 写钱包余额和 append-only ledger。
5. 订单标记 paid/fulfilled，记录 provider transaction ID。
6. 返回“首次履约”或“已履约”，重复回调不重复入账。

### 4.3 退款状态机与余额冲正

退款必须拆成安全的三步：

1. `begin_refund_atomic`：锁订单，检查可退款金额与历史退款，创建唯一退款记录并进入 `submitting`。
2. 服务端按订单 `payment_provider` 调用对应渠道，使用退款记录 ID 作为幂等号。
3. `finalize_refund_atomic`：确认外部退款成功后，原子冲正用户钱包、写退款账本、更新退款与订单状态。

用户余额已消费时必须明确选择一种策略：

- 默认拒绝自动退款，进入人工审核；或
- 允许形成负债并冻结付费功能，直到还清。

禁止“外部已退款但站内余额保持可用”。

### 4.4 四账对账

每日/每小时对账至少覆盖：

1. 支付渠道账：provider transaction/refund。
2. 订单账：payment_orders/payment_refunds。
3. 钱包账：wallet_accounts 与 wallet_ledger 汇总。
4. 资源账：image/video/voice/LLM task、usage、revenue、debt。

建立只读对账视图/任务，输出：订单缺钱包、钱包缺订单、资源已交付未结算、已结算无资源、退款未冲正、余额与账本汇总不符。异常进入人工队列，不自动掩盖。

### 4.5 安全边界

- 新建统一 `safeFetch`：仅 http/https；拒绝用户名密码、危险端口；DNS 解析后拒绝 IPv4/IPv6 回环、私网、链路本地、组播和云元数据；每次重定向重新验证；限制超时、字节、内容类型和跳数。
- LLM/图片/视频普通接口不接受任何 endpoint、proxy URL、api key、provider、internal model name。用户只传公开模型 ID，服务端查表映射。
- 所有对象查询使用 `(resource_id,user_id)`，管理员走独立、审计过的路径。
- 上传生成随机对象 key，文件名只作显示元数据；使用 magic bytes；SVG/HTML/JS/XML 默认拒绝或转码隔离；所有本地路径做 `resolve` 后根目录包含检查。
- 限流迁移到 Redis/数据库，维度至少包含用户、IP、路由、设备；只信任受控反向代理写入的 IP 头。
- 提示词保护采用“精准拒绝 + 输出防泄露”：只拒绝索取系统提示、内部规则、密钥、渠道和工具配置的意图；正常业务讨论不拦截。输出侧检测提示词指纹/canary；日志只记录规则 ID、hash 和脱敏短摘要。

## 6. D：无真实费用测试矩阵

所有上游支付、图片、视频、语音、LLM 均使用 mock adapter；数据库使用隔离测试库或本地 Supabase。禁止命中真实域名。

| 类别 | 测试 | 预期结果 |
|---|---|---|
| 并发扣费 | 余额 100，并发 100 个 3 元请求 | 仅资金允许的请求成功；余额不负；成功数、ledger 数和资源数完全一致 |
| 同幂等键 | 同一扣费请求重放 100 次 | 只扣一次，返回同一 ledger/reservation 结果 |
| 余额不足 | 余额小于 reserve 金额 | 上游 mock 调用次数为 0，钱包与流水不变 |
| 流水故障 | 注入 ledger insert 失败 | 整个事务回滚，余额不变，资源不提交 |
| 重复回调 | 同一已签名 callback 并发 100 次 | 只入账一次，只产生一条 callback 记录和一条入账 ledger |
| 回调金额 | `NaN`、`Infinity`、负数、少付、多付、错误小数位 | 全部拒绝，不修改订单或钱包 |
| 回调渠道/币种 | A 渠道订单收到 B 渠道回调；币种错误 | 拒绝并记录脱敏安全事件 |
| 回调崩溃点 | 在 callback 入库、钱包入账、订单置 paid 各点注入故障 | 全事务回滚或可幂等恢复，不重复入账 |
| 状态补偿 | 两个同额订单和一笔管理员充值 | 未付款订单不能因同额流水变 paid |
| 退款重放 | 同一退款并发 20 次 | mock 网关只收到一个幂等退款；钱包只冲正一次 |
| 退款余额已花 | 可用余额不足以冲正 | 自动退款被拒绝或进入 debt/manual_review；不会留下可用余额 |
| 图片预授权 | mock 生成成功/失败/超时 | 成功 settle；失败/超时 release；未 reserve 不调用上游 |
| 视频异步 | 提交、轮询、重复成功回调、取消、过期 | 每任务只结算一次；取消/过期只释放一次 |
| LLM 流式 | 正常完成、客户端断开、usage 缺失、超 token | 预授权存在；实际结算有上限；断开后可恢复结算或释放 |
| 语音 | 同一文本请求重放、上游失败、账单记录失败 | 同幂等键只生成/结算一次；失败释放；账单与钱包同事务或可对账 |
| BOLA 视频 | 用户 A 请求用户 B 的 task ID | 统一 404，不泄露是否存在，不发生轮询/扣费 |
| BOLA 会话 | 用户 A 使用用户 B 的 conversation ID | 拒绝；owner 与消息均不改变 |
| SSRF | `localhost`、私网、link-local、IPv6、本地 DNS、重定向、DNS rebinding | 全部在请求发出前或每跳校验时拒绝 |
| 上传 | 假 MIME、SVG 脚本、polyglot、超大文件、`../` 文件名 | 拒绝；存储根外无文件；内存受控 |
| 公开 API | 递归 snapshot 检查响应键 | 不出现 provider/channel/key/endpoint/proxy/internal model id/protocol/成本统计 |
| 提示词保护 | 套取系统提示、冒充管理员、编码变体 | 拒绝且不泄露；正常写作/智能体配置讨论正常通过 |

| 四账对账 | 构造漏 ledger、漏 task、重复 callback、退款未冲正 | 对账任务逐项发现并输出可追踪异常 ID |

## 8. 修复顺序与发布门禁

1. 立即封禁客户端自定义 LLM endpoint/proxy，并修复视频 task 与会话所有权。
2. 上线数据库钱包事务、幂等唯一索引和 reservation；切换所有付费生成入口。
3. 上线支付履约与退款状态机，删除文本查重和余额变化推断。
4. 收口所有 SSRF/上传入口，拆分公开/管理员模型 DTO。
5. 上线分布式限流、日志脱敏、提示词输出防泄露。
6. 运行完整无费用测试矩阵。
7. 通过支付 sandbox 和管理员人工验收后，才允许真实充值与付费模型。

发布门禁必须同时满足：

- 并发扣费、重复回调、退款重放、BOLA、SSRF、公开 DTO 测试全绿。
- 四账对账差异为 0，或所有历史差异均有人工处置记录。
- 任何资源成功交付都有唯一 reservation/settlement/ledger/task 链路。
- 任意扣费失败时，付费上游不会被调用或结果不会被无偿交付。

## 9. 回滚点

- 使用 `BILLING_LEDGER_V2` 与 `PAYMENT_FULFILLMENT_V2` 功能开关分阶段切换。
- 迁移先增表/增列/增索引，不立即删除旧表或旧字段；先 shadow-write 和只读对账。
- 切换前保存四账快照与迁移前备份。
- 代码回滚可切回旧读路径，但新账本只能保留、不能删除或覆盖；回滚后暂停真实付费，直到完成对账。
- 新 RPC/索引的 SQL rollback 只能在确认无 V2 数据写入或完成数据迁回后执行。
- 支付/退款状态机一旦产生外部交易，不允许靠数据库回滚“撤销”外部事实，必须走补偿交易与人工对账。

## 10. 审计结论

当前实现的主要风险是系统性资金完整性缺失，而不是简单的某个弹窗、某个接口或某条日志。最小正确路径是：数据库原子账本和幂等约束先行，所有付费资源改为预授权，支付与退款改为状态机，再处理 UI 与体验层优化。在这些门禁完成前，不建议做真实充值或真实付费生成验收。
