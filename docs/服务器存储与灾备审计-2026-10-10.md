# 服务器存储与灾备审计（2026-10-10）

> 本文只记录只读核验结果。核验期间没有改挂载、停服务、写数据库、调用 COS、迁移数据或切换生产。

## 结论

当前状态是“应用文件与大部分共享数据已脱离系统盘，但正式 PostgreSQL 仍在系统盘；存在部分 COS 快照，但尚不具备完整、可演练、可独立恢复的灾备能力”。因此，存储安全门禁当前为 **不通过**，不能仅凭 `/data` 已挂载就判定可以安全切换生产。

## 实际存储图

|---|---|---|---|
| 正式 PostgreSQL 用户、钱包、账务、任务、历史与审计数据 | `/var/lib/pgsql/data`，数据库 `zimeiti_prod` | 60G 系统盘 `/dev/vda1` | 高风险；已确认是线上正在使用的正式库，不是空库或历史残留 |

| Commerce SQLite、素材与运行状态 | `/data/web/shared/runtime` | 独立挂载盘 | 已脱离系统盘，但仍是单机 SQLite/文件系统架构 |
| 公共/发现素材 | `/data/web/shared/assets` | 独立挂载盘 | 已脱离系统盘，约 5.2GB |
| 语音 SQLite 与参考音频 | `/data/web/shared/voice` | 独立挂载盘 | 已脱离系统盘；访问隔离仍需加固 |

| 托管视频及部分生图结果 | 腾讯 COS | 对象存储 | 代码与运行环境已配置，但版本控制、加密、跨区复制和生命周期尚无控制台读回证据 |

## 已确认事实

- `/data` 是 `/dev/vdb` 上的 ext4 独立挂载，约 200G；当前约 54% 已用、约 87GB 可用。
- `/data` 使用 UUID 写入 `/etc/fstab`，但包含 `nofail`。数据盘缺失时系统仍可启动。
- 正式 Web、共享数据、素材、日志、语音与备份路径都位于 `/data/web`。
- `/data/web/releases` 已占约 26.6GB，`/data/direct-deploy` 已占约 5.3GB；当前空间尚可，但没有“当前版本加两个回滚锚点”的自动清理和空间/inode 水位告警证据。
- 正式 Web 由 root 身份下的 PM2 运行；PM2 服务没有 `RequiresMountsFor=/data` 或 `ConditionPathIsMountPoint=/data`。
- PostgreSQL 监听在 `127.0.0.1:5432`，物理目录位于系统盘；线上应用连接本地 PostgREST/本地 PostgreSQL。
- 正式库身份与线上规模一致：4 个用户，约 433 条视频任务和 442 个用户文件记录。
- PostgreSQL 已开启 `fsync` 和 `full_page_writes`，但 `archive_mode=off`、`data_checksums=off`，没有 PITR/WAL 归档证据。
- 2026-10-10 03:10 的 COS JSON 快照成功：33/33 张固定表，11,965 行，0 张表报告失败。
- 正式库 `user_files` 已记录 385 个腾讯 COS 对象、约 1.87GB：其中生图工作台 234 个/约 1.11GB，视频生成 111 个/约 593MB，工具箱视频提取 5 个/约 130MB；这证明已有真实媒体元数据指向 COS，但本次未调用 COS，不能替代对象存在性、版本控制和加密策略读回。
- 最近一份可被 `pg_restore --list` 读取的完整格式 dump 生成于 2026-10-09 05:37，仍保存在同一台服务器的 `/data` 盘；未发现每日完整 dump 计划。
- 每日 02:30 的备用机同步计划任务已失效：所引用脚本不存在，日志持续报告 `No such file or directory`。
- 数据库中的正式备份运行、保留证据、RPO/RTO 回执、恢复演练与恢复校验记录均为 0。
- 未看到近 30 天 `/data` 的 ext4/I/O 错误；这只能证明当前没有已记录的磁盘错误，不能代替备份。
- 服务器存在一个 COS 磁盘镜像脚本，但它默认是从 COS 拉到本地、未加入计划任务，且依赖的 `coscmd` 未安装；它不能被视为当前有效备份。

## 发布前阻断项

1. 正式 PostgreSQL 仍在系统盘，系统盘故障会直接影响正式用户与账务数据。
2. 没有覆盖 PostgreSQL、应用 JSON、Commerce SQLite/素材、语音 DB/音频、上传文件和 COS 对象字节的完整加密异地备份。
3. 备用机同步任务已失效。
4. 没有真实恢复演练，无法证明备份可恢复。
5. PM2 和发布脚本未对 `/data` 挂载丢失做启动前阻断；存在落回系统盘或启动失败的风险。
6. COS 版本控制、服务端加密、跨区/跨账号复制、生命周期策略都缺少控制台或 API 读回证据。
7. 本地凭据登记和服务器历史备份中存在明文敏感材料；本次证据未保存任何密钥值，但相关凭据必须在供应商侧轮换。
8. 发布包、旧 release、incoming 和日志缺少已执行的容量保留上限，长期会挤满数据盘。

## 合格整改顺序

### A. 不停机先做

1. 给部署和 PM2 增加 `/data` 真实挂载点、UUID/设备、root 所有 marker、空间与 inode 水位的 fail-closed 门禁。
2. 修复或删除失效的备用机同步计划，避免继续制造“有备份”的假象。
3. 建立每日完整 PostgreSQL custom-format dump、SHA-256、加密、COS/异机副本和保留策略；任何表失败必须让任务整体失败。
4. 为应用 JSON、Commerce SQLite 与素材、语音 DB 与音频、上传和公共素材生成一致性快照及 SHA-256 清单，并保存到独立故障域。
5. 读回 COS 的版本控制、加密、生命周期和复制状态；只看环境变量存在不算启用证明。
6. 轮换已暴露或落入明文登记/备份的密钥，并把登记文件改成只记录受控位置。

### B. 维护窗口内做

1. 将正式 PostgreSQL 迁移到独立受保护数据盘或托管 PostgreSQL。不能简单把目录复制到 `/data` 后继续运行，必须先冻结写入、校验 dump/restore 或一致性复制、再原子切换。
2. 启用并验证 PITR/WAL 归档；对恢复点、账本连续性、用户数、任务数、资金总额和关键表哈希做核对。
3. Web 服务降权运行，并为服务启动增加数据盘挂载依赖。

### C. 切换前验收

1. 在隔离环境从异地备份恢复整套 PostgreSQL、Commerce、语音、素材和配置。
2. 模拟 `/data` 缺失、系统盘损坏、对象被删除、磁盘满和恢复到新服务器。
3. 记录 RPO、RTO、恢复步骤、行数/账务/文件哈希比对与失败回滚证据。
4. 只有恢复演练通过，存储门禁才可由“不通过”改为“通过”。
