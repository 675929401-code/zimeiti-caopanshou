## 根因证据

### Omni Flash 1080p

- 数据库配置启用、非隐藏、密钥与端点齐全，供应商模型清单返回 200 且精确包含目标模型。
- 同一数据库行和同一绑定凭据在 2026-08-15 10:20:50 有成功任务；15:03 后连续返回 `user quota is not enough`。
- 供应商未提供可用的无费用余额/视频额度查询端点，因此“站内平台费用充足”不能证明绑定视频凭据仍有额度。
- 结论：额度属于供应商绑定凭据的视频子账户，不是本地现金余额，也不是错绑模型 ID。此次未再次发起 Omni 付费任务。

安全重试条件：渠道 C 运维方明确确认当前绑定凭据的视频额度已补足；无费用模型清单仍包含目标模型；随后仅提交一个最小任务，并核对任务 ID、终态 URL、长期转存和单次账单。

### MiniMax H3

- 无费用 `/v1/models` 返回 200，但当前凭据清单未列出 H3，诊断为 `MODEL_NOT_LISTED_FOR_KEY`；真实 POST 随后仍识别模型并创建任务，说明该供应商的模型清单对 H3 分组并不完整，不能单独据此判死活。
- 附件文档写 4–15 秒；实时接口对 4 秒请求返回“最小 5 秒”。兼容逻辑已调整为 4 秒目标提交 5 秒，成功后由统一持久化链路裁切到 4 秒。
- 附件和供应商HTTP 400原始响应都明确：分辨率只接受 `720p`、`2k`、`4k`，不存在 `1080p`。数据库旧配置 `[720p,1080p,4K]` 是本地错误；已改为 `[720p,2K,4K]`，适配器把UI的`2K`转换为上游小写`2k`，旧卡片携带`1080p`时不再原样发送。
- 已使用现有公网参考图，未重新付费生图。预计 UI 价格 ¥1.50/次。
- 唯一有效供应商任务：`6ff69769f28540ee8e72c449ee20e3f1`；约 30 秒后终态失败，供应商原始状态为 `server_error`，没有 `video_url`。
- 本地历史状态 `failed`、`price_charged=0`，`cash_transactions` 对任务内部 ID 和 `video:<外部任务ID>` 均为 0 条。
- 文档说明失败会释放预扣；供应商没有余额查询端点，故只能确认本地未扣款和供应商失败终态，不能独立读取供应商账本金额。为避免重复费用，模型现已停用并从公共模型列表移除。

### Grok 20秒渠道 D

- 数据库配置完整且目标模型出现在认证后的 `/v1/models` 清单。
- 真实生成端点的既有证据为连续 HTTP 503；不是缺少本地通道、密钥或模型映射。
- 旧适配器在每次提交前用 POST `health_check` 探测，可能无意创建计费请求；已改为 GET 模型清单的无费用契约检查。
- 503 现统一转译为“渠道服务暂时不可用”，不再误报“当前没有可用通道”。若真缺配置，后台会记录精确缺失字段，用户侧只显示可操作的配置不完整提示。

## 全链路修复

链路已逐段核对：公开模型 ID → `/api/video/generate` → 协议适配器 → 数据库密钥/渠道配置 → 请求字段 → 异步任务 ID → `/api/video/stream` 与 `/api/video/status` 轮询 → 公网参考图 → 长期对象存储 → 成功扣费/失败零扣费 → 视频历史与媒体历史。

主要修复：

- 新增统一错误分类；用户响应、SSE、视频历史和媒体历史均只返回脱敏提示，原始供应商诊断只留在后台日志/健康记录。
- 公共模型接口对普通用户和管理员都只返回不透明模型 ID、公开名称、渠道字母、能力和公开价格；不再因管理员登录态泄露内部整行配置。
- 渠道字母从配置名称稳定解析，修正媒体历史把 H3/Omni 错标为 C/D 的问题；当前为 H3=A、Omni=C、Grok20s=D。
- 失败提交和异步失败都写入历史，费用固定为 0。
- 成功任务用 `finalizing` 条件更新抢占终态；账单再按 `reference_id` 查重，避免并发轮询重复扣费。
- 成功视频保存供应商 URL，并转存长期对象存储；4→5 秒兼容任务成功后在转存时裁切。
