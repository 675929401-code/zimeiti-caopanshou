# AutoDL H3 生产部署拓扑与运维契约

日期：2026-08-21  
适用范围：自媒体操盘手 V2.6 主站、MiniMax H3 自租实例、AutoDL 生命周期控制器  
验收边界：本文只定义部署和运维契约；不包含 Developer Token、Gateway Bearer key、SSH 私钥、真实实例 UUID 或数据库密钥。

## 1. 结论

`127.0.0.1:16011` 不是用户电脑依赖。它表示**运行 Next.js 主站和生命周期 worker 的部署服务器本机回环端口**。当前运行时在这台服务器上创建 SSH 本地转发：

```text
用户浏览器
   │ HTTPS
   ▼
自媒体操盘手 Next.js（Linux / PM2，端口 5000）
   ├── AutoDL 控制面：https://www.autodl.art（状态、快照、开机、关机）
   ├── Supabase：任务队列、租约、fencing token、最终入账
   └── 127.0.0.1:16011
           │ ssh -L 127.0.0.1:16011:127.0.0.1:6011
           ▼
       AutoDL 实例 SSH
           └── 127.0.0.1:6011 H3 Gateway
                   └── 127.0.0.1:6006 ComfyUI / GPU
```

只要 Next.js 进程与 `ssh -L` 进程处于同一个 Linux 网络命名空间，这个设计就是正确的。当前最稳妥、可部署的形态是 **Linux 主机 + PM2 单进程 fork**。

Docker 也能使用回环隧道，但前提是 Next.js 与 SSH 客户端在同一个容器内；当前 Dockerfile 尚不满足生产条件，见第 9 节。

## 2. 当前支持与禁止的拓扑

| 拓扑 | 状态 | 运维契约 |
|---|---|---|
| Linux + PM2，1 个 `next start` | 推荐 | Next instrumentation 启动 worker；该进程拥有 SSH tunnel；PM2 负责主进程重启 |
| Docker 单容器：Next + SSH | 原理可行、当前未就绪 | 容器内安装 `openssh-client`；同一容器内绑定 `127.0.0.1:16011`；只读挂载 key/known_hosts |
| PM2 cluster / 同机多个 Next 进程 | 禁止 | 共享主机端口空间，会争抢 `16011`；进程切换时还存在旧 tunnel 残留窗口 |
| 多台 Web 服务器都开启 lifecycle | 暂不推荐 | 数据库租约可 fencing，但每台都会启动 contender；应只在一个专用 controller 副本开启 lifecycle |
| 用户浏览器直连 AutoDL 6006/6008/6011 | 禁止 | 会绕过服务端密钥、租约、计费最终化和 SSRF/输入约束 |

## 3. PM2 生产配置清单

### 3.1 主机依赖

- Node.js、pnpm、PM2 与当前主站版本兼容。
- OpenSSH client 可执行文件固定为 `/usr/bin/ssh`。
- `curl` 用于人工本机健康检查，不参与业务请求。
- PM2 只运行一个名为 `agent-hub` 的 `next start -p 5000` 进程；不得设置 `instances > 1` 或 `exec_mode: cluster`。
- 首次主机配置执行一次 `pm2 startup`，每次部署的 `pm2 save` 负责保存当前进程表。

### 3.2 持久化目录

建议固定以下布局：

```text
/data/agent-hub/
├── env/
│   └── .env.local                         # 0600，不进 Git
└── secrets/
    └── autodl-h3/                         # 0700
        ├── id_ed25519                     # 0600
        ├── known_hosts                    # 0600 或 0644
        ├── developer.token                 # 0400 或 0600
        └── gateway.token                   # 0400 或 0600
```

部署脚本已把 `/data/agent-hub/env/.env.local` 链接到每个不可变 release 的 `.env.local`。`developer.token` 与 `gateway.token` 必须是单行、不大于 16 KiB 的普通文件，由 PM2 服务用户（或运行进程的 root）拥有，且 group/other 权限位必须为零。不要把 Developer Token、Gateway key 或 service-role key 写入仓库、数据库模型记录、`NEXT_PUBLIC_*` 或 PM2 ecosystem 源码。

### 3.3 SSH key 与 known_hosts

运行时要求 SSH executable、private key、known_hosts 都是已存在的绝对普通文件；Linux 私钥的 group/other 权限位必须为零。

`AUTODL_H3_SSH_HOST_KEY_ALIAS` 必须设为一个固定别名（推荐 `autodl-h3-production`），`known_hosts` 必须提前在该别名下写入**已人工核对**的主机公钥。运行时从官方 snapshot 动态获取 `proxy_host`/`ssh_port`，但 OpenSSH 始终以固定别名查找已钉住的 key；端点旋转不会自动信任新 key。禁止在生产启动过程中自动运行 `ssh-keyscan` 并直接信任结果；应从 AutoDL 控制台或其他可信通道核对指纹后再落盘。

更换 GPU 实例或 host key 后，若新指纹未核对并更新到固定别名条目，系统应保持 fail-closed，而不是关闭 `StrictHostKeyChecking`。

## 4. 环境变量与分阶段启用

空值安全模板位于 `docs/autodl-h3-production.env.example`。Linux 生产环境优先通过 server-only secret file 读取两个敏感凭据：

- `AUTODL_DEVELOPER_TOKEN_FILE`：AutoDL 控制面高权限凭据文件，只用于状态/快照/开关机。未显式指定时也会检查 `/run/secrets/autodl-developer-token`。
- `AUTODL_H3_SELFHOST_API_KEY_FILE`：实例内 Gateway Bearer key 文件，只用于 H3 数据面。未显式指定时也会检查 `/run/secrets/autodl-h3-selfhost-api-key`。

两者不能互换。`AUTODL_DEVELOPER_TOKEN` 与 `AUTODL_H3_SELFHOST_API_KEY` 仅是受控环境变量回退；Windows 当前用户 DPAPI 仅作开发环境回退，不是 Linux 生产依赖。模型数据库记录只应保存 `secret://autodl-h3-selfhost` 引用，不能保存明文 Gateway key，更不能保存 Developer Token。

推荐按三阶段启用，每次改动保护环境文件后重启 PM2：

| 阶段 | `LIFECYCLE_ENABLED` | `DRY_RUN` | `ATOMIC_FINALIZER` | `ALLOW_POWER_ACTIONS` | 目的 |
|---|---:|---:|---:|---:|---|
| 0 安装前 | false | true | false | false | 完全不读 H3 凭据、不触网、不启动 worker |
| 1 观察 | true | true | true | false | 验证依赖注入、租约、状态机和隧道，不执行开关机/真实提交 |
| 2 正式 | true | false | true | true | 开启真实调度、自动开机与空闲关机 |

硬约束：`ALLOW_POWER_ACTIONS=true` 时 `ATOMIC_FINALIZER_ENABLED` 必须为 true，否则运行时拒绝安装。空闲关机默认和最小值均为 300 秒。

## 5. 启动、重启与恢复契约

### 5.1 主站启动

Next.js `instrumentation.register()` 只在 Node runtime 中加载。顺序必须是：

1. 安装生产 runtime：Supabase store、AutoDL control client、SSH tunnel、H3 dispatcher、atomic finalizer。
2. 安装成功后启动 lifecycle worker。
3. worker 使用每进程随机 owner ID，获取数据库实例租约并用 fencing token 保护状态更新。

当前两个启动入口均已把 worker 启动绑定到 runtime 安装结果：只有 `installed=true` 或 `reason=already-installed` 才会创建 worker。功能关闭或安装失败时直接返回，不参与数据库租约竞争。水平扩展时仍只允许一个 controller 副本启用 lifecycle。

### 5.2 PM2 重启

- PM2 自动重启 `next start`。
- 新进程重新执行 instrumentation，并生成新的随机 worker owner ID。
- 旧租约过期后，新 owner 可接管；lease 默认 30 秒，操作期间每约三分之一 lease 周期续租。
- 若 AutoDL 实例仍在运行，新 runtime 会先探测本机 `16011`；不可用时获取新 snapshot 并重建 SSH tunnel。
- runtime 已注册 `SIGINT`/`SIGTERM`/`exit` 退出清理，主进程终止时会调用 `tunnel.stop()`；不会吞掉框架既有的 signal handler。
- 新 SSH child 只在 `ExitOnForwardFailure` 稳定窗口通过后才能接受 ready，避免把旧的/非当前进程拥有的 `16011` 监听误判为新 tunnel。`SIGKILL` 或主机崩溃无法执行进程内 cleanup，所以 PM2 重启后仍必须依赖端口所有权与 ready 门禁，不得扩展为 cluster。

### 5.3 AutoDL 实例启动

官方 `power_on` 请求固定携带以下服务端启动命令（不接受浏览器、任务 payload 或管理员表单覆盖）：

```text
bash /root/zealman-app/scripts/improved-autostart.sh
```

该命令用于开机后尽早启动 Zealman/ComfyUI 服务。AutoDL 官方只保证接收开机请求，不保证 `start_command` 成功，因此它不能替代后续的 `running`、snapshot、SSH 隧道和 `/health/ready` 检查。

生命周期运行时通过 SSH 执行：

```text
/bin/bash /root/codex-h3-gateway/start_all.sh
```

远端脚本先启动 ComfyUI，再启动只监听 `127.0.0.1:6011` 的单 worker Gateway。Gateway 的 `/health/ready` 同时检查工作流文件、ComfyUI 队列与磁盘空间。

当前远端进程脚本仍有两个运维边界：

1. PID 文件只使用 `kill -0`，未核对 PID 对应的命令，存在 PID 复用误判。
2. `start_gateway.sh` 等待 `/health/live`，不是 `/health/ready`；主站会继续重试 ready，但脚本本身可能提前报告成功。

Gateway `v0.2.1` 已关闭重启恢复 P0：启动时先验证已落盘结果，再只读查询既有 ComfyUI `prompt_id`/history/queue；仍在执行的 prompt 只重新挂接轮询，绝不重新提交 GPU 工作。无法证明成功的任务会收敛为明确、可恢复的失败，并要求新的幂等键后才能由调用方显式重试。

## 6. 健康检查矩阵

健康状态要分层判断，不能只看到主站 HTTP 200 就认为 H3 可生成：

| 层级 | 检查位置 | 判定 |
|---|---|---|
| 主站进程 | `pm2 jlist` / `http://127.0.0.1:5000/` | `agent-hub` 单实例 online，主站返回 200 |
| 静态部署契约 | 离线脚本 | PM2 profile 无 blocking；Docker profile 在未修复前应失败 |
| runtime 安装 | PM2 服务端日志 | 不出现固定诊断 `production runtime install failed` |
| worker | 服务端受限运维状态/日志 | worker 为预期 `dry-run` 或 `active`，owner 唯一，lease 可续期 |
| 本机 tunnel | 部署服务器本机 | `127.0.0.1:16011/health/ready` 返回 ready；不得从浏览器公网探测 |
| 远端 Gateway | 通过 tunnel | workflows、ComfyUI、disk 三类 check 均为真 |
| 任务恢复 | 状态存储 | 无超期 `DISPATCHING/UPSTREAM_RUNNING/RESULT_STAGING/FINALIZING` |
| 自动关机 | 状态机 | 只有 activity 全为 0 且 idle 连续达到 300 秒，才能进入关机准备和执行 |

现有 `scripts/health-check.sh` 只验证主站和 PM2，不足以证明 H3 worker、SSH tunnel 或 Gateway ready。它也仍保留旧 cron 注释；不要把它当作 H3 全链路健康检查。

## 7. 单 worker、租约与水平扩展

当前有三层互斥，职责不同：

1. Next 进程内 `Symbol.for(...)`：防止同一进程重复启动 interval。
2. Supabase instance lease + job lease + fencing token：防止不同进程同时修改生命周期和任务状态。
3. AutoDL Gateway 的 asyncio lock + `gpu-admission.lock`：把 GPU 执行通道限制为 1。

数据库 lease 不等于本机 TCP 端口所有权。PM2 cluster 进程共享同一个 `127.0.0.1:16011`，旧 owner 或孤儿 SSH 进程可能占着端口。因此当前运维契约是：

- `agent-hub` 只允许一个 PM2 fork。
- 水平扩展 Web 时，仅一个专用 controller 副本设置 `AUTODL_H3_LIFECYCLE_ENABLED=true`；其余副本为 false。
- tunnel 已有显式进程退出清理，但本地端口仍是排他资源，且 `SIGKILL`/宿主崩溃可绕过 cleanup。在引入独立 controller entrypoint、显式 leader election 和可观测 heartbeat 前，不宣称任意多副本安全。

## 8. 零网络验收

以下脚本只读本地源码和空值模板；不会加载应用、读取真实 `.env.local`、打开 socket、查询数据库、调用 AutoDL、开关机或提交生成：

```powershell
node scripts/verify-autodl-h3-deployment-topology.mjs --profile pm2
node scripts/verify-autodl-h3-deployment-topology.mjs --profile docker
node scripts/verify-autodl-h3-deployment-topology.mjs --profile all --json
```

PM2 profile 的目标是 `PASS_WITH_WARNINGS` 或 `PASS`，且 `blocking=0`。当前 Docker profile 应因第 9 节两个硬缺口返回非零退出码。警告不能被解释为生产验收通过，应按第 10 节分级处置。

## 9. Docker 当前阻塞项

Docker 模式现在不能作为 H3 生产部署依据：

1. Dockerfile 复制 `.next/standalone`，但 `next.config.ts` 中 `output: "standalone"` 被注释，构建产物契约不一致。
2. runner image 未安装 `openssh-client`，无法创建 `ssh -L` tunnel。
3. runner 使用 UID 1001；只读挂载的 mode-0600 私钥必须由 UID 1001 可读。known_hosts 也必须在容器内为绝对路径。
4. runtime 已原生支持 `*_FILE` 以及 `/run/secrets` 默认路径；Docker secret 必须以普通文件挂载，对 runner UID 1001 可读且 group/other 权限位为零。不能把 secret COPY 进镜像层。

修复后仍必须保持 Next 与 SSH 在同一网络命名空间。如果将 SSH 变成 sidecar，硬编码的 `127.0.0.1:16011` 不会跨普通容器网络工作，除非二者共享 network namespace。

## 10. 发布前缺口分级

| 级别 | 缺口 | 最小处置 |
|---|---|---|
| 已关闭 | production runtime 安装失败后 worker 仍启动并可能竞争 lease | 两个启动入口已显式依赖 install success；继续保持单 controller 部署 |
| 已关闭 | Gateway 重启不恢复/终结持久化非终态 job | Gateway v0.2.1 已按落盘结果、prompt history 与 queue 幂等对账；恢复路径禁止重新提交 GPU 工作 |
| 已关闭 | SSH child 缺少主进程退出清理 | 已增加 SIGTERM/SIGINT/exit cleanup、动态 snapshot 端点更换及固定 `HostKeyAlias` 验收；仍保持单 fork，不将进程内 cleanup 视为 `SIGKILL` 保证 |
| P1 | Gateway PID 仅 `kill -0`，启动只看 live | 校验 cmdline，并等待 ready 或返回明确 warming 状态 |
| P1 | H3 缺少独立、受保护的主站运维健康面 | 提供不含 secret/host 的内部 status，展示 install/mode/lease/tunnel/gateway checks |
| P1（Docker） | standalone 与 openssh-client 缺失 | 修正构建模式、安装 SSH client、制定 secret mount 契约 |

在 P0 缺口关闭、静态验收通过且完成一轮受控重启恢复演练前，环境变量应停留在阶段 0 或阶段 1，不应直接开启真实 power actions。
