# 品牌事实源与消息触达闭环审计

日期：2026-10-02  
范围：长期清单任务 3、4。  
口径：代码存在、数据库合同存在、真实生产者/消费者、当前本地数据、浏览器完成门槛分别记录；不以“有表或有 API”冒充闭环。

## 结论

- **任务 3 仍为部分完成。** 单站品牌版本控制面、图片资产、草稿、发布、回滚、CAS、不可变事件和主要前台读取者已形成源码链；当前本地数据库没有任何品牌修订、图片资产或事件，公共读取仍是 `legacy-fallback`，因此没有“真实上传 → 发布 → 重启读取 → 回滚”的当前数据和浏览器证据。
- **任务 4 仍为部分完成。** 系统公告和账户通知已有真实数据与消费者，P0 强制退出、P1 账户通知、P2/P3 公告、P4 试用引导已有单弹窗优先级；视频顶部通知、旧 `popup_pushes` 和统一消息控制面尚未贯通。统一消息 8 张表当前全部 0 行，不能称迁移完成。

### 已验证的客户端策略

- 单弹窗顺序为 P0 安全/强退 > P1 账户通知 > P2 紧急公告 > P3 普通公告 > P4 试用引导。
- 公告按 `announcement_id + push_revision` 执行 `frequency_hours`、`max_impressions` 和 `require_ack`；重推版本不会继承旧版本次数。
- 公告和账户收件箱读取失败会显示错误和重试，不再伪装为“暂无消息”。
- 当前公告展示次数仍是“当前浏览器、当前账号”的客户端 ledger；跨设备展示次数没有服务端权威计数。

### 本轮局部修复

1. `/api/notifications?raw=1` 现在要求 `announcements.manage`，禁用草稿不再向普通访问者公开。
2. 视频通知数据源失败现在返回明确 `503` 和 `success:false`，不再用空数组冒充没有通知；模型推荐源失败会单独标记 `recommendationsAvailable:false`，不影响管理员通知。
3. 手工账户通知发送改为 `announcements.manage` + 二次解锁 + 幂等键 + `enqueue_user_notification_once` + 成功/失败治理审计；拒绝绕过卡密和邀请礼包专用链。
4. 敏感设置读取和写入改为服务端强制权限及二次解锁，不依赖前端是否显示入口。

### 任务 4 的下一最小闭环

1. **先停止新增旧通道。** 在拥有后台页的统一窗口删除“视频平台顶部已发布”承诺，或将该编辑器改成创建 `category=video` 的统一消息活动；在真实消费者和回执完成前不能显示“已发布”。
2. 将公告、账户通知、试用弹窗和视频横幅各接一个“旧业务 → 统一 outbox”的事务适配器，并建立旧记录到 `delivery_id` 的映射；旧历史只读保留。
3. 先交付一个统一铃铛收件箱和一个表面策略执行器，所有展示/阅读/点击/关闭/抑制写 `message_events`，失败由租约 worker 重试并进入死信。
4. 把频率和最大展示次数移到账号投递状态，客户端 ledger 只作离线优化；跨设备由服务端事实决定。
5. 最后退役 `platform_settings.video_notifications` 和 `popup_pushes` 写入口，保留只读迁移期后再删除，不做双写常态化。
