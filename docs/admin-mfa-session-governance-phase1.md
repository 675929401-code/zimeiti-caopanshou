# 管理员 MFA 与会话治理第一阶段

日期：2026-10-03  
状态：源码候选；未构建、未接入后台页面、未应用数据库迁移、未发送邮件

## 事实审计

当前已经具备：

- `user_auth_sessions` 是服务端会话事实源；登录会原子签发会话，第三次登录撤销最旧会话，最多保留两个在线会话。
- JWT 带 `sessionId`，每次管理员鉴权都回查数据库；会话撤销后，旧 JWT 下一次请求即失效。
- 退出登录只撤销当前会话；密码或登录身份变化会撤销该账号全部会话。
- `admin_step_up_sessions` 已用管理员登录密码或平台管理密码提供 10 分钟敏感操作解锁，并绑定当前授权档案版本和权限范围。
- 登录日志能提供账号关联的失败登录记录；会话表保存 IP 与 User-Agent 的不可逆哈希。

当前不能声称具备：

- 普通邮箱验证码登录不是 MFA。它与密码是两种可选登录方式，没有“密码成功后仍必须完成第二因子”的串联门禁。
- 验证码目前是单 Node 进程内存状态；多进程、重启和登录前原子消费均没有耐久证据。
- User-Agent/IP 哈希不是可信设备凭据；换网、代理和共享出口会变化，也不能证明设备持有人身份。
- 登录路由目前会在密码正确后直接创建 `user_auth_sessions` 和 JWT，没有 pending-login 挑战状态。
- 当前没有可信设备随机令牌、到期/撤销记录，也没有地理定位或“不可能旅行”可信来源。

## 本阶段实现

独立 API：`/api/admin/login-logs/sessions`

- GET：需要 `security.view`，只读取当前管理员自己的会话；不接受目标用户 ID。
- POST `revoke_session`：仍是当前管理员自助范围，要求 `security.view` + 有效 step-up；精确代理权限映射不会放宽其他登录日志写操作。
- 服务端 HMAC 会话句柄替代原始 `session_id`；响应不包含原始 IP、User-Agent 或哈希值。
- 同源浏览器写校验、JSON/4KB 上限、幂等键、进程内并发锁、耐久审计查重、5 分钟 8 次撤销限流和治理审计均在路由中执行。
- 当前会话撤销需显式确认，成功后同时清除登录与 step-up Cookie；其他设备会话撤销后立即失效。
- GET 使用 30 秒按管理员/当前会话/请求指纹隔离的进程内缓存和 singleflight，客户端每 60 秒至多自动读取一次；页面隐藏或离线时中止并暂停。
- 风险区只汇总账号关联的 24 小时失败登录数与当前会话指纹变化，明确提示这不是攻击者身份结论。

独立组件：`AdminAccountSecurityPanel`

```tsx
<AdminAccountSecurityPanel
  token={token}
  canManage={tabAccess.security === true}
  stepUpReady={adminAccess?.stepUp.status === "ready"}
  onRequestUnlock={() => setUnlockDialogOpen(true)}
  autoRefresh
/>
```

组件不依赖 `super-admin` 页面，可由有 `security.view` 的普通管理员使用。建议在安全中心新增独立“管理员会话”目标视图并懒加载；不要塞进超级管理员人员列表。界面同时展示真实会话、风险线索，以及 MFA/可信设备/异常挑战的明确未接入状态。

## 后续 MFA 闭环（未执行）

候选结构保存在 `supabase/design-only/20261003_admin_mfa_trusted_devices.sql`。它不会被正常迁移自动应用。完整闭环必须按以下顺序实现和验收：

1. 备份并在本地隔离数据库应用候选结构，验证 RLS、service role、到期、次数上限、单次消费和并发挑战。
2. 密码验证成功后只创建一次性 pending-login nonce；此时不得创建 `user_auth_sessions`、JWT 或登录 Cookie。
3. 使用管理员账号已经绑定的邮箱发送用途隔离的 MFA 验证码；只保存验证码哈希和目标地址哈希，发送失败时挑战失败关闭。
4. 以数据库事务原子增加失败次数、消费验证码；成功后才签发服务端会话和 JWT，验证码不可重放。
5. 可信设备只能在一次 MFA 成功后签发 256 位随机 HttpOnly、Secure、SameSite=Strict Cookie；数据库只保存令牌哈希，默认 30 天，支持单设备和全部设备撤销。
6. 异常信号触发时忽略可信设备，重新进入 MFA；IP/地区只作线索，不能单独封号或认定攻击者。
7. 对登录、挑战、可信设备签发/使用/撤销和失败限流写入不可变审计；响应和日志不包含验证码、Cookie、原始令牌或完整邮箱。
8. 真实 SMTP 送达、多进程共享、重启恢复、两设备上限、会话撤销、跨站请求、并发重放和管理员浏览器页面全部通过后，才把 MFA 状态从 unavailable 改为 ready。
