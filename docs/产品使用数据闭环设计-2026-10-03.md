# 产品使用数据闭环设计（PRODUCT-USAGE-EVENTS-R697）

## 当前结论

本轮已经建立代码链和数据库设计，但 `supabase/design-only/20261003_product_usage_events.sql` **尚未应用**，本地、候选和生产数据库均不能据此声称已经具备完整产品分析事实源。部署前还必须配置经过审查的 `PRODUCT_USAGE_POLICY_BASIS_CODE` 与 `PRODUCT_USAGE_NOTICE_VERSION`；任一缺失，采集 API 返回 503 且不写入事件。

现有 `operation_flight_events` 用于回答“哪个请求/任务在什么阶段成功、失败或超时”。它记录操作域、阶段、结果、耗时和错误指纹。**操作事实不等于产品分析**：它没有统一页面、功能、会话心跳、激活 cohort、留存和价值里程碑，也不覆盖所有只读浏览行为。因此它只能在新事实源缺失时显示“最近 24 小时有限运行信号”，不能计算 DAU、WAU、MAU、激活率、留存、功能采用或价值路径。

## 已落地的链路

1. 全局 `DiagnosticSentry` 在明确的用户页面白名单上记录 `page_view`。
2. 可见且在线的页面使用单次 `setTimeout` 每 5 分钟记录一次 `session_heartbeat`；页面隐藏、离线或卸载时停止，不使用常驻 `setInterval`。
3. 现有同源 fetch 哨兵对真实聊天 POST 记录 `workflow_started`。只有非流式、非 202 且 HTTP 成功的同步终态才记录 `workflow_completed`；流式响应拿到响应头不等于生成完成，因此不伪造完成。HTTP 或网络失败记录 `workflow_failed`，只携带枚举错误码。
4. 客户端只能提交严格白名单字段，不存在通用 metadata：事件、功能、页面、里程碑、入口、数值耗时和步骤序号。
5. `/api/product-usage/events` 进行同源校验、当前用户会话鉴权、6KB 请求限制、20 条批次限制、每用户每分钟请求/事件双限流、批内重复检查和数据库主键去重。
6. 用户 ID 由服务端登录态归属；浏览器会话 UUID 和工作流 journey UUID 在服务端使用密钥 HMAC 后才允许持久化。
7. `/api/admin/product-usage` 同时经过统一后台代理和路由内 `logs.view` 权限校验，响应 `private, no-store`。每管理员 60 秒最短读取间隔，共享 60 秒缓存与 singleflight，429 携带 `Retry-After`。
8. `ProductUsagePanel` 展示事实源状态、DAU/WAU/MAU、7 日激活、D1/D7/D30、功能采用与价值路径。任何缺失都显示“— / 不可用”，不回退为 0。

## 事件合同

允许的事件：

- `page_view`：访问一个稳定 page key，不上传 URL 查询参数。
- `session_heartbeat`：页面可见且在线时的低频活跃信号。
- `feature_open`：明确打开核心功能。
- `workflow_started`：真实提交一个工作流；必须有 journey UUID。
- `workflow_completed`：得到可验证终态；必须有 journey UUID。
- `workflow_failed`：得到失败终态；必须有 journey UUID，只允许安全 reason code。
- `value_milestone`：保存、下载、导出、发布等明确价值节点；必须有里程碑枚举。

当前不接收或保存：提示词、对话正文、生成结果、素材 URL、邮箱、原始网络地址、UA 原文、任意 metadata、任意页面 URL 或查询参数。

## 指标口径

| 指标 | 定义 | 当前数据要求 |
|---|---|---|
| DAU | 统计日内至少一条合规事件的去重会员 | `product_usage_daily_user_facts` |
| WAU | 含统计日在内最近 7 个自然日至少一条合规事件的去重会员 | 同上 |
| MAU | 含统计日在内最近 30 个自然日至少一条合规事件的去重会员 | 同上 |
| 7 日激活 | 注册后 7 天内至少完成一次工作流的新会员 / 已完整观察 7 天的同期新会员 | users + lifecycle |
| D1/D7/D30 | 首次使用日 cohort 在第 1/7/30 个自然日再次产生合规事件 | lifecycle + daily facts |
| 功能采用 | 近 30 天使用某功能的会员 / MAU，并同时给出完成人数 | daily facts |
| 价值路径 | 活跃 → 打开功能 → 启动工作流 → 完成工作流 → 价值里程碑 | daily facts |

人数为 1–4 的群组隐藏精确人数和比例；k 下限固定为 5，调用者不能调低。0 只有在事实源已部署、覆盖窗口明确且真实聚合结果为 0 时才可显示。事实表/聚合函数缺失、无合规事件或响应不完整时使用 `null + reasonCode`。

## 耐久数据设计

设计文件包含三层：

- `product_usage_events`：180 天原始白名单事件，主键去重，只有服务端角色可写/读。
- `product_usage_daily_user_facts`：按日、会员、功能汇总，控制实时面板读取成本。
- `product_usage_user_lifecycle`：每会员的首次/最近使用与首次工作流节点，用于激活和留存 cohort。

插入触发器只更新上述汇总表。聚合函数 `read_admin_product_usage_snapshot_v1` 只返回人数与比例，不返回用户 ID、会话 HMAC 或 journey HMAC。原始事件到期删除必须由单独审查的调度器执行，本轮没有启用调度器。

## 资源控制

- 客户端心跳间隔 5 分钟，页面隐藏或离线停止。
- 客户端批次最多 20 条，请求体最多 6KB。
- 单用户每分钟最多 30 个请求、120 条事件；当前门禁为进程内防突发，横向扩容后应追加 Redis/数据库分布式门禁。
- 管理面板每管理员最短 60 秒读取一次，共享缓存与 singleflight 防止相同聚合重复执行。
- 聚合优先调用数据库汇总 RPC；fallback 最多读取 501 条飞行记录，只返回 500 条并标注截断。
- 没有供应商调用、模型调用、支付提交或自动业务修复。
