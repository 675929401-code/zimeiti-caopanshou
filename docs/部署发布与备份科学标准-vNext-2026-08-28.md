## 1. 一页结论

本项目以后遵循以下发布链：

```text
开发工作树
  → Git（源码、审计、版本）
    → CI 干净 Linux 构建（一次）
      → 不可变制品（Web / Voice 分开）
        → TCR 镜像仓或 COS 制品仓
          → 服务器按 digest/SHA 拉取候选
            → 健康检查
              → 原子切换
                → 观察与自动/人工回滚
```

同时建立独立的数据链：

```text
数据库/会员/余额/订单/任务元数据 → 数据库备份与 PITR
用户上传/生成结果              → 私有对象存储 + 元数据一致性备份
公开示例/图片/视频/音频         → 内容哈希 COS + CDN + 版本化 manifest
密钥                            → Secret Manager/服务器密钥注入
日志与验收证据                  → 独立日志/证据归档
```

六条强制原则：

1. **Git 只负责源码和审计，不充当生产运行目录，也不保存会员数据、用户素材或密钥。**
2. **每次代码发布都产出完整、不可变的“受影响服务制品”；局部发布是少发布一个服务，不是复制几个源码文件。**
3. **构建只在 CI 的固定 Linux 环境执行一次；生产服务器只拉取、校验、启动和切换，不执行 `git pull + install + build`。**
4. **大图片、视频和音频不进入普通 Git、Web 镜像或 Voice 镜像，改用 COS/CDN 内容寻址与 manifest。**
5. **数据库、会员、余额、订单、任务、用户文件和密钥永远位于不可变制品之外；部署不得覆盖或删除它们。**
6. **没有 release manifest、制品哈希、备份点、候选健康检查和回滚目标，就不允许进入生产。**

## 2. 为什么当前部署容易形成“大杂烩”

2026-08-28 本地只读盘点得到：

| 项目 | 当前事实 |
|---|---:|
| 当前事实源总量 | 约 20.39GB |
| 按现有 `.releaseignore` 得到的 release | 约 2.78GB |
| release 中 `public` 占比 | 94.75% |
| `public/storyboard-reviews` | 约 1.36GB |
| `public/youcai-media` | 约 1.04GB |
| 上述两个目录占整个 release | 86.51% |
| 本地 `node_modules` | 约 1.66GB |
| 本地 `.next` | 约 123.65MB |

现有 Dockerfile 会复制完整 `node_modules`、完整 `public` 和 `.next`，仅这三项原始体量就不低于约 4.45GB。当前 `next.config.ts` 又未启用可验证的 standalone 输出，所以“每次完整上传耗时巨大”是现有边界造成的必然结果，不是 Git 本身的缺陷。

同时存在以下结构性风险：

- 本地事实源目前不是一个干净 Git 工作树，源码事实源、发布仓副本和运行版本可能漂移。
- 旧文档同时出现 Docker/Nginx 与宿主机 PM2 两种互相冲突的生产形态。
- Web 与 Voice 是两个独立构建单元，但旧运行配置没有把二者作为同一复合发布进行版本记录。
- `.releaseignore` 只排除了部分 uploads，没有排除两大公共媒体库和研究材料。
- `.gitignore` 重新包含了 `public/**/*.mp4` 等视频，普通 Git 会背负线上媒体分发职责。
- `.gitattributes` 没有 LFS 规则；但即使补 LFS，也不应让数 GB 生产媒体跟随应用发布。
- `.npmrc` 未被 release 显式排除；在证明无凭据前，必须按敏感文件处理。
- 可变 JSON、uploads、数据库、素材 manifest、构建产物和源码的边界没有形成机器可验收的 allowlist。
- 当前 migration 静态盘点创建了 36 张表，但 `backup-data.sh` 的固定表清单与 `cos-data-snapshot.mjs` 均遗漏其中 34 张；遗漏范围包含 Canvas、钱包账本、图片/语音请求、短剧和 Skill 等新业务域。
- 现有两个数据备份脚本遇到表导出失败会跳过并继续；COS snapshot 仍可能写出 manifest，因而存在“不完整备份被误认成成功”的风险。
- 当前数据导出主要是明文 JSON；源码存在不等于已经启用 PITR、客户端加密、COS 版本控制、SSE-KMS、跨地域复制或恢复演练，这些线上状态均需单独验证。
- `data/*.json` 仍包含可写运行数据，engine config 类型还可能携带凭据字段；`.releaseignore` 只排除了个别文件，没有把整个 mutable data 域外置。
- 实际对象域不止腾讯 COS，还包括 Supabase Storage `avatars`、Coze S3 和本地 provider；只备份数据库和一个 COS bucket 会形成缺口。

## 3. 标准分层

### 3.1 源码治理层：Git

Git 中应保存：

- `src/**`、受支持的 Web/Voice 源码；
- `package.json`、根 `pnpm-lock.yaml`、Voice 自己的 lockfile；
- 数据库 schema、migration 和只包含非敏感数据的 seed；
- 测试、verifier、Dockerfile、CI/CD 定义、部署脚本；
- 非敏感 `.env.example`、配置 schema；
- 素材 manifest、对象 key、SHA-256、MIME、尺寸、时长和授权来源；
- 少量、经过明确 allowlist 的黄金测试 fixture。

Git 中禁止保存：

- `.env*` 真值、token、cookie、JWT、SSH key、云密钥、数据库连接串；
- 未审计的 `.npmrc`；
- `node_modules`、开发机 `.next`、缓存、日志、临时目录；
- 用户上传、用户生成结果、会员数据、余额、订单和数据库备份；
- `public/storyboard-reviews`、`public/youcai-media` 等大批生产分发媒体；
- `.codex-*`、`.tmp-*`、本地快照、E2E 录像、截图和运行证据；
- PM2 日志、PID、运行时数据库、WAL/SHM 文件。

Git 仓库标准：

- 建立一个干净的私有 `origin` 作为产品源码主仓；
- 建立不同故障域的只读/镜像 `backup` 远端；
- `main` 受保护，禁止直接 push 和 force-push；
- 日常开发走 `codex/*` 或 feature 分支，经 CI 和评审合并；
- release tag 只指向已经产出并验证制品的 commit；
- 每次发布固定完整 commit SHA，不使用漂移的分支名或 `latest` 作为唯一依据；
- Git push、CI build、artifact publish、production deploy 是四个独立状态，必须分别记录。

Git LFS 仅用于少量必须具备 Git 评审语义的设计母版/黄金样本；线上图片、视频、音频仍由 COS/CDN 分发。

### 3.2 构建与验收层：CI

CI 是唯一正式构建者。参考环境必须是与生产一致的 Linux/amd64 容器或 runner，固定：

- Node 主版本和精确基线；
- pnpm 版本；
- 根 lockfile 与 Voice lockfile；
- OS 基础镜像 digest；
- Chromium、ffmpeg、字体、`sharp`、`better-sqlite3` 等原生依赖基线。

开发机 Windows 只用于开发和本地检查，不是生产制品来源。

最小 CI 门禁顺序：

```text
checkout exact SHA
→ secret scan / forbidden-file scan
→ release allowlist 与体量门禁
→ pnpm frozen-lockfile 验证
→ TypeScript / ESLint
→ release preflight
→ 聚焦业务 verifier
→ Web/Voice 构建
→ 制品内启动与健康检查
→ SBOM/依赖与漏洞报告
→ 生成 SHA-256/digest
→ 签发 release manifest
→ 发布到制品仓
```

任何门失败，后续阶段全部停止。禁止 `--frozen-lockfile` 失败后自动退回可修改 lockfile 的安装。

### 3.3 制品层：不可变 Web / Voice

Web 与 Voice 必须分开构建、分开打包、分开回滚：

```text
Web artifact
  port: 5000
  source: 根 package.json + 根 pnpm-lock.yaml

Voice artifact
  port: 5001
  source: voice-platform/package.json + voice-platform/pnpm-lock.yaml
```

短期过渡形态：

- CI 生成 `web-<release-id>.tar.zst` 和 `voice-<release-id>.tar.zst`；
- 上传 COS 制品仓；
- 服务器解包到独立 release 目录；
- PM2 管理宿主机进程；
- symlink/受控路径原子切换。

长期目标形态：

- Web 与 Voice 分成两个 OCI 镜像；
- 推送腾讯云 TCR；
- 服务器按 image digest 拉取并运行；
- 容器由 Docker Compose/systemd/编排器管理；
- OCI 容器内不再叠加 PM2 作为第二套 supervisor。

选择规则：

- 需要尽快稳定现有 PM2 运维：先上 `tar.zst + immutable releases`；
- 需要高频发布、原生依赖一致、镜像层差异传输：迁移 OCI + TCR；
- 不采用生产服务器 `git pull + pnpm install + next build`。

### 3.4 素材与 CDN 层

公开可缓存素材采用内容哈希路径：

```text
cos://<public-bucket>/media/sha256/<sha256>.<ext>
cos://<public-bucket>/asset-manifests/<manifest-digest>.json
```

私有用户素材采用租户隔离路径和签名访问：

```text
cos://<private-bucket>/uploads/<tenant>/<user>/<yyyy>/<mm>/<asset-id>
cos://<private-bucket>/generations/<tenant>/<task-id>/<asset-id>
```

素材发布顺序必须是：

```text
计算内容 SHA-256
→ 上传新对象 key
→ 校验大小、hash/CRC、MIME、宽高/时长
→ 生成并校验新 manifest
→ 提升 manifest digest
→ 验证页面播放/展示/下载
→ 观察期结束后再做旧对象生命周期处理
```

二进制对象使用不可变长缓存；manifest 使用短缓存和显式版本。CDN 只是分发缓存，不是备份。对象存储应启用版本控制、生命周期和异地/异账号副本。

迁移本地 `public` 的顺序：

1. 先为 `storyboard-reviews` 与 `youcai-media` 建立可兼容的 manifest/CDN URL 层；
2. 上传二进制并完成 URL、CORS、poster、播放和降级验证；
3. manifest 留在 Git，二进制从 release allowlist 排除；
4. 再迁移 cover、help、demo、short-drama、avatars；
5. 未证明无动态引用的文件不得直接删除。

### 3.5 数据与状态层

以下对象是“业务状态”，不属于应用制品：

- 用户、会员等级、订阅、权益；
- 钱包、余额、扣费、退款、账单、订单；
- 幂等键、请求记录、任务状态、生成历史；
- Canvas/项目/配置的持久化状态；
- 用户文件 metadata 与实际对象字节；
- Supabase Storage、COS、Coze 或其他供应商资产的归档关系；
- 后台动态配置、运行开关和审计记录。

部署脚本不得自动执行会破坏或隐式同步 schema 的命令。migration 是独立 job，遵循：

```text
备份点
→ staging 演练
→ expand/向后兼容 migration
→ 旧代码兼容验证
→ 新制品发布
→ 观察窗口
→ 后续独立 contract migration
```

删除列、重命名、不兼容约束、数据重写等 contract migration 不得和新代码首次上线绑在同一次不可逆切换中。

### 3.6 密钥、配置、日志和证据层

- 密钥由 CI Secret、云 Secret Manager 或服务器权限受控 env 文件注入；
- 仓库只保存配置 schema 和无真值模板；
- runtime config 必须区分 DEV/STAGING/PROD，并在启动前进行必填项和格式验证；
- 日志进入独立目录/集中日志系统，不写入 release 目录；
- 验收截图、报告、trace 和账单证据进入独立归档，不进入产品 Git 和镜像；
- 日志与证据输出必须脱敏，禁止打印 token、cookie、JWT、完整连接串和用户隐私。

## 4. 三种发布模式

### 4.1 FULL：复合全平台发布

触发条件：

- Web 与 Voice 同时改变；
- 共享 DTO、认证、计费、任务协议改变；
- 有数据库 migration；
- Node/Next/pnpm/基础镜像升级；
- 大规模目录或运行架构调整。

产物至少包括：Web 新制品、Voice 新制品、asset manifest（如变化）、migration set、复合 release manifest。

### 4.2 SERVICE：受影响服务局部发布

触发条件：

- 只改导航、Canvas、页面或根 API：只构建和发布 Web；
- 只改 Voice：只构建和发布 Voice；
- 一个服务内部的普通 bugfix。

关键定义：

> “局部发布”是只发布受影响的服务；不是在服务器上覆盖一个 `.tsx`、`.js`、`.next` chunk 或若干文件。

即使只改一个 `.tsx`，也必须重新生成该服务完整制品，因为 Next.js 的 BUILD_ID、路由 manifest、Server Functions、客户端 chunk hash、服务端 bundle 和 output trace 必须属于同一次构建。否则很容易产生“新服务端 + 旧客户端 chunk”或“新源码 + 旧 manifest”的混合状态，表现为导航卡顿、跳转异常、hydration 错误、画布无法编辑或静态资源 404。

SERVICE 发布前必须回答：

- 新 Web 是否兼容当前 Voice？
- 新 Voice 是否兼容当前 Web？
- 是否改变共享协议、认证、计费或 schema？
- 是否需要同步更新 asset manifest？

任一答案不确定或不兼容，自动升级为 FULL。

### 4.3 ASSET/CONFIG：素材或运行配置发布

适用：

- 新增/替换图片、视频、音频；
- 更新运行时读取的 asset manifest；
- 后台动态配置变化，不影响编译期代码或 schema。

如果素材被 TypeScript 静态 import、被 Next 构建时嵌入 bundle，或 manifest 在构建时导入，那么它不是纯 ASSET 变化，必须升级为 Web SERVICE 发布。

## 5. 变更分类决策树

```text
是否只有内容哈希素材/运行时 manifest 改变？
  是 → ASSET
  否 ↓

是否只有 voice-platform 内部且不改变共享协议/schema？
  是 → SERVICE: voice
  否 ↓

是否只有 Web 内部且兼容现有 Voice/schema？
  是 → SERVICE: web
  否 ↓

是否涉及共享 DTO、auth、billing、migration、Node/Next/基础镜像？
  是 → FULL
  不确定 → BLOCKED，完成兼容评审后再分类
```

## 6. Release Manifest：一次发布的唯一身份证

每次制品发布必须生成机器可读 manifest，例如：

```json
{
  "schemaVersion": 1,
  "releaseId": "prod-20260828T160000Z-a1b2c3d",
  "environment": "production",
  "mode": "SERVICE_WEB",
  "source": {
    "repository": "private-origin",
    "commit": "<full-commit-sha>",
    "tag": "release/prod-20260828T160000Z-a1b2c3d"
  },
  "services": {
    "web": {
      "artifact": "cos://artifacts/web/<release-id>.tar.zst",
      "sha256": "<artifact-sha256>",
      "buildId": "<next-build-id>",
      "port": 5000
    },
    "voice": {
      "reusedFromRelease": "<previous-release-id>",
      "artifactSha256": "<current-voice-sha256>",
      "port": 5001
    }
  },
  "assets": {
    "manifest": "cos://asset-manifests/<digest>.json",
    "sha256": "<manifest-sha256>"
  },
  "database": {
    "schemaVersionBefore": "<version>",
    "schemaVersionAfter": "<version>",
    "migrations": [],
    "backupPoint": "<backup-id-or-pitr-time>"
  },
  "runtime": {
    "node": "<pinned-version>",
    "pnpm": "9.0.0",
    "osImageDigest": "<digest>"
  },
  "rollback": {
    "targetReleaseId": "<previous-good-release-id>"
  },
  "builtAt": "<RFC3339>",
  "promotedAt": null
}
```

`/api/version`、日志、部署历史和运维面板至少能对应到：`releaseId + commit + BUILD_ID + Web/Voice artifact digest + asset manifest digest`。

## 7. 服务器部署方法

### 7.1 近期：tar.zst + PM2 不可变目录

建议目录：

```text
/srv/zimeiti/
├─ artifacts/
│  ├─ web/
│  └─ voice/
├─ releases/
│  ├─ web/<release-id>/
│  └─ voice/<release-id>/
├─ current-web    -> releases/web/<active-id>
├─ current-voice  -> releases/voice/<active-id>
├─ previous-web
├─ previous-voice
├─ shared/
│  ├─ env/web.env
│  ├─ env/voice.env
│  ├─ logs/
│  ├─ tmp/
│  └─ runtime-data/
└─ deploy-state/
   ├─ deploy.lock
   ├─ active.json
   └─ history.jsonl
```

标准步骤：

1. 运维只提交 `releaseId`，部署器读取已签发 manifest；
2. 获取部署锁，禁止两次发布并发修改 active 状态；
3. 下载受影响服务的制品到 staging 文件名；
4. 校验 SHA-256、文件大小、manifest 与目标环境；
5. 解包到全新的 `<release-id>` 目录，禁止覆盖 `current-*`；
6. 注入该环境的只读配置/密钥引用；
7. 在候选端口启动 Web/Voice；
8. 检查版本、健康、首页、关键导航、Canvas 入口和 Web→Voice rewrite；
9. 仅在全部通过后原子切换 symlink/受控入口并 graceful reload；
10. 切换后再执行一次外部健康检查；
11. 写入 `active.json` 与 append-only `history.jsonl`；
12. 保留上一可用 release，观察期结束后按保留策略清理更早制品。

失败规则：候选失败不触碰 current；切换后失败立即指回 previous 并恢复上一复合 release manifest。

PM2 cluster 模式可使用 graceful reload，但应用必须正确响应关闭信号并停止接收新请求。Web 与 Voice 应分别拥有 app 定义和独立健康检查。

### 7.2 长期：OCI + 腾讯云 TCR

标准命名：

```text
<tcr>/zimeiti/web:<release-id>
<tcr>/zimeiti/web@sha256:<digest>
<tcr>/zimeiti/voice:<release-id>
<tcr>/zimeiti/voice@sha256:<digest>
```

部署只使用 digest；tag 仅帮助人阅读。镜像层应把稳定依赖放前、频繁变化源码放后，并使用 BuildKit cache/registry cache。大媒体不进入镜像层，否则一个媒体改变会使巨大 layer 失效。

OCI 的“完整制品”并不意味着每次重新上传全部字节：registry 按内容 digest 复用未变化 layer，只传缺失 blob。正因为如此，逻辑上可获得完整、可回滚制品，物理上仍能进行差异传输。

## 8. 环境标准

| 环境 | 用途 | 数据 | 发布方式 | 允许构建 |
|---|---|---|---|---|
| DEV | 开发和本地静态检查 | 本地/脱敏 | 本地运行 | 允许，但不产生生产制品 |
| CI | 唯一正式构建 | fixture/脱敏 | exact SHA | 允许，且为唯一正式构建者 |
| STAGING | 生产前验收/恢复演练 | 脱敏生产结构 | 与生产相同制品 | 禁止现场构建 |
| PROD | 真实用户服务 | 真实业务数据 | 按 digest/SHA 拉取 | 禁止现场构建 |

强制要求：

- STAGING 与 PROD 的 OS、Node、原生库和启动方式一致；
- 配置值不同，但配置 schema 相同；
- PROD 不允许手工修改 release 目录；
- 紧急修复仍先形成 commit 和不可变制品；
- 数据库环境完全隔离，不允许 staging 指向 production；
- 线上版本判断以 `/api/version` 和 release manifest 为准，不以浏览器旧标签或本地源码为准。

## 9. 备份标准

### 9.1 3-2-1-1-0 原则

- 至少 3 份数据副本；
- 至少 2 种存储介质/故障域；
- 至少 1 份异地或异账号；
- 至少 1 份不可变/对象锁副本；
- 定期恢复演练，目标 0 个未解释恢复错误。

### 9.2 备份对象、目标 RPO/RTO 与保留

以下是上线目标，不是当前已实现承诺：

| 对象 | 权威来源 | 备份机制 | 目标 RPO | 目标 RTO | 建议保留 |
|---|---|---|---:|---:|---|
| Git 源码与 tag | 私有 origin | backup remote + 每日 git bundle | 5 分钟 | 1 小时 | tag 永久；bundle 90 天/月度长期 |
| 发布制品与 manifest | TCR/COS | 跨故障域复制 + digest 校验 | 15 分钟 | 30 分钟 | 至少最近 20 次和 90 天 |
| 账号/会员/角色/权益 | 主数据库 | PITR/WAL + 每日逻辑备份 + 不可变副本 | 5 分钟 | 2 小时 | PITR 30 天；日备 35 天；月备 1 年 |
| 钱包/余额/账本/订单/计费/幂等 | 主数据库 | 连续 PITR + 每日加密快照 + 账本不可变归档 | 1 分钟 | 核心恢复 1 小时；完整对账 4 小时 | 按财务/法务期限，建议不少于 7 年，最终以合规确认值为准 |
| 普通业务表/Canvas/任务历史 | 主数据库 | PITR + 每日逻辑备份 | 15 分钟 | 2 小时 | 日备 35 天；月备 1 年 |
| 私有上传/生成资产 | 私有对象存储 | 版本控制 + 跨桶/跨账号复制 + inventory | 15 分钟 | 4 小时 | 依业务/合规；删除有宽限期 |
| 公开示例素材 | 版本化 COS | 内容哈希 + 版本控制 + 异地副本 | 24 小时 | 4 小时 | 被 manifest 引用期间不得删除 |
| 用户文件 metadata | 数据库 | 与对象 inventory 同批次一致性快照 | 15 分钟 | 2 小时 | 与对象生命周期一致 |
| 密钥与证书 | Secret Manager | 受控版本/加密离线恢复包 | 24 小时 | 2 小时 | 当前 + 历史轮换版本 |
| 审计/部署/安全日志 | 日志平台 | 分层存储 + 不可变审计归档 | 5 分钟 | 4 小时 | 180–365 天，按合规确定 |
| 本地开发快照 | 工作站 | 独立归档桶/备份盘 | 24 小时 | 1 个工作日 | 短期，不能替代 Git/数据库备份 |

### 9.3 数据库备份必须 fail-closed

数据库脚本不得只维护一份容易过时的手写表名 allowlist。标准做法：

1. 从 migration/schema 自动得到预期对象清单；
2. 从数据库 catalog 得到实际对象清单；
3. 对两者做差异检查；
4. 缺表、多表、导出失败、行数/校验不匹配都使备份任务失败；
5. 只有所有对象成功、manifest 完整、hash 可核验时才能发布 `BACKUP_SUCCESS`；
6. 失败 manifest 必须标记失败，不能让不完整备份伪装成成功快照。

高风险表（会员、余额、账单、扣费、退款、幂等和任务）除全库备份外，要有聚焦的行数、金额守恒、外键/业务关联和恢复后核对。

当前修复门必须把“36 张 migration 表与备份清单静态差异为 0”作为 CI 断言；不能在旧手写 allowlist 上继续逐表打补丁。钱包还必须验证 `balance_before + delta = balance_after`、末条账本余额与用户读模型一致、同一幂等操作只有一次账本影响。

### 9.4 对象字节和数据库 metadata 必须成对恢复

仅恢复 `user_files` 或任务记录而不恢复 COS/Supabase Storage 实际对象，页面仍会得到失效 URL；仅恢复对象而不恢复 metadata，用户也无法在历史中找到文件。

每个一致性快照至少记录：

- 数据库 backup/PITR 标识；
- 对象 inventory 版本；
- 对象 key、version ID、大小、hash/ETag、MIME；
- metadata 主键、用户/租户、task ID、asset ID；
- manifest digest；
- 快照时间和允许的一致性窗口。

供应商临时 URL 不能视为备份；任务成功后应把资产归档到自有对象存储，并让历史记录指向稳定 owned asset。

恢复后的 `queued/running/processing` 任务必须先进入人工对账/恢复仲裁状态。不得因为恢复数据库而重新提交供应商任务、重复扣费或重复交付。

匿名 Canvas 的本地草稿可以改善浏览器内编辑体验，但不是服务器灾备 Source of Truth。只有持久化到账号并进入数据库/对象联合快照后，才能纳入正式 RPO/RTO 承诺。

### 9.5 恢复演练

备份只有经过恢复才算有效。最低频率：

- 每月：随机选一个数据库日备，在隔离环境恢复并跑 schema/行数/金额/关联 verifier；
- 每月：抽样恢复公开与私有对象，校验 hash、权限、播放/下载；
- 每季度：从 Git commit + lockfile + 制品/构建链恢复一个完整 staging；
- 每季度：执行一次 Web/Voice release 回滚；
- 每半年：演练“主数据库不可用 + 对象存储误删 + 密钥轮换”的组合灾难恢复；
- 每次演练记录实际 RPO/RTO、差异、负责人和修复截止时间。

## 10. 体量和内容门禁

从 denylist 改为 release allowlist。目标：

- Git/源代码 release context：目标 25–60MB，硬门建议先设 100MB；
- 非 allowlist 单文件超过 5–10MB：失败；
- 新 MP4/MP3/大 PNG 进入普通 Git：失败；
- `node_modules`、`.next`、`.codex-*`、`.tmp-*`、backups、uploads、数据库、日志：失败；
- `.env*` 真值、`.npmrc`、常见密钥模式：失败且日志脱敏；
- 缺根 lockfile、lockfile 漂移、安装需要改 lock：失败；
- 产物缺 release manifest、SHA/digest 或版本接口不匹配：失败。

首次迁出 `storyboard-reviews` 与 `youcai-media` 后，按当前盘点 release 可从约 2.78GB 降到约 374.7MB；再迁出 research/research-output 后约 250.4MB。完成 allowlist 与精选静态资源后，目标可进一步进入约 25–60MB 的源码/构建上下文区间。

## 11. 回滚标准

### 11.1 代码/服务回滚

- 不重新构建旧 commit；直接使用上一已验证 artifact digest/SHA；
- 回滚 Web 或 Voice 前检查复合兼容矩阵；
- 若共享协议变化，回滚到上一完整 composite release；
- symlink/容器切换后进行版本与关键链路复验；
- 写入 append-only 部署历史，记录原因、操作者、时间和证据。

### 11.2 数据库回滚

- 默认采用 expand/contract，尽量避免代码回滚需要 schema 逆迁移；
- migration 前记录 PITR/备份点；
- 不把破坏性 SQL 逆操作做成自动回滚；
- 数据恢复先在隔离环境验证，再按事故流程执行；
- 恢复时同时核对对象存储和业务 metadata。

### 11.3 素材回滚

- 内容哈希对象不覆盖；
- 回滚只提升旧 manifest digest；
- 旧对象在所有 manifest 引用和观察窗口结束前不得清理。

## 12. 实施路线

### Phase 0：本地发布链收口（当前）

- 补齐并冻结根 `pnpm-lock.yaml`；
- 本地 release preflight 默认只允许 prepare，publish/deploy 继续 fail-closed；
- 修复导航与 Canvas 源码链并通过静态/零费用 verifier；
- 建立本 vNext 规范；
- 不构建、不重启 5000、不推 Git、不连生产数据库、不部署服务器。

完成定义：源码检查通过，但不声称线上已生效。

### Phase 1：建立干净 Git 主仓

- 从 allowlist 生成首个干净源码快照；
- 运行 secret scan、大文件门禁和 lockfile 冻结检查；
- 建立私有 origin + 独立 backup remote；
- 保护 main、建立 PR/CI、tag 和 commit 签名策略；
- 将旧 `Git发布仓` 和“当前版本”副本在核验后降级为只读历史/迁移来源。

完成定义：从干净 clone 可重复完成所有本地 verifier；尚不等于生产部署。

### Phase 2：素材解耦

- 定义 asset manifest schema 和 CDN base URL；
- 先迁两大媒体目录，再迁 cover/help/demo/avatars；
- 对象上传、hash、权限、CORS、播放/下载和旧 URL 回退全部验收；
- 完成引用迁移后才从 release allowlist 排除二进制。

完成定义：干净 clone 不依赖数 GB 本地媒体也能构建；staging 可正常展示素材。

### Phase 3：tar.zst + PM2 标准部署

- 在固定 Linux CI 构建 Web/Voice 独立运行制品；
- 建立 COS 制品仓、release manifest 和服务器 immutable 目录；
- staging 演练候选端口、原子切换、回滚和磁盘清理；
- 通过后再安排生产切换窗口。

完成定义：服务器不再现场 build，能够按 releaseId 部署并在分钟级回滚。

### Phase 4：备份链修复与恢复门

- 备份表清单改为 schema/migration 自动发现；
- 先消除当前 36 张 migration 表中遗漏 34 张的静态缺口；
- 任一导出失败则整次备份失败；
- 明文 JSON 改为客户端加密/受控密钥引用，并为每个对象记录 SHA-256；
- 将整个 mutable `data/`、uploads、日志和备份目录外置于 release；
- 把 Supabase Storage、COS、Coze S3 和本地 provider 全部纳入对象 inventory；
- 建立数据库 + 对象 inventory 一致性快照；
- 开启版本控制、不可变副本和异地/异账号复制；
- 完成月度/季度恢复演练。

完成定义：有可重复恢复证据，不再只看“备份脚本运行过”。

### Phase 5：OCI + TCR（稳定后）

- Web/Voice 分镜像；
- 启用 standalone/output tracing 或等价 production prune；
- 使用 BuildKit 与 registry cache；
- 服务器按 digest 部署，移除容器内 PM2；
- 保留 tar 路线作为阶段性回滚，直到 OCI 连续稳定若干发布。

## 13. 每次上线的 Go/No-Go 清单

上线前必须全部为 YES：

- [ ] 来源是干净 origin 的 exact SHA；
- [ ] main 保护和 CI 通过；
- [ ] secret scan、forbidden-file scan、体量门禁通过；
- [ ] 根/Voice lockfile 冻结安装通过；
- [ ] 变更模式 FULL/SERVICE/ASSET 已确定；
- [ ] Web↔Voice↔schema 兼容矩阵已确认；
- [ ] migration 已分类，生产前备份点存在；
- [ ] 受影响服务构建和制品内启动通过；
- [ ] artifact/asset digest 与 release manifest 一致；
- [ ] staging 使用同一制品通过关键链路；
- [ ] 服务器磁盘、端口、配置、密钥引用和旧 release 可用；
- [ ] 候选健康、版本接口和外部健康通过；
- [ ] 回滚 releaseId/digest、负责人和触发阈值明确；
- [ ] 数据库/对象恢复证据仍在有效期；
- [ ] 发布窗口和观察窗口已安排。

任一项为 NO 或 UNKNOWN：**NO-GO**。
