# 白标多租户设计与实施计划（2026-11-24）

## 一、目标

让客户用自己的域名访问你的系统，看到自己的品牌；客户自己的用户、会员、消耗、订单与统计彼此隔离；平台方保留总控与计费能力。行业里这叫 **White-label / Multi-tenant SaaS**，不是“换 Logo”。

## 二、行业标准形态（对标成熟 SaaS）

| 层 | 行业做法 | 你现在 |
|---|---|---|
| 域名 | 客户 CNAME 到你；TXT/CNAME 验证；自动签发 TLS；按 Host 路由 | 已有 TXT 认领 + 品牌草稿，缺 CNAME/TLS 闭环 |
| 品牌 | 每租户一份品牌配置，草稿→发布，公开页只读已发布版本 | 已有（单品牌维度） |
| 租户 | 租户主数据 + 生命周期（试用/正式/暂停/欠费） | 只有 1 行默认租户，无开通流程 |
| 成员 | 用户↔租户多对多 + 角色（owner/admin/member） | `tenant_members` 表存在，0 行，无管理入口 |
| 数据隔离 | 行级 `tenant_key` + Postgres RLS；对象存储按租户前缀 | 业务表无 tenant_key，无 RLS |
| 计费 | 租户钱包/额度 + 价目表 + 按租户归属的消耗流水 | 无租户维度 |
| 后台 | 平台控制台（开通/配额/总览）+ 租户控制台（自己用户/消耗/品牌/域名） | 只有平台后台 |
| 审计 | 所有跨租户操作、代登录、域名变更留痕 | 有 tenant_audits 表，未接入 |

**选型建议**：行级 `tenant_key + RLS`（共享库），不要一租户一库。你的规模用共享库最稳，成本低、迁移简单；等单租户体量很大再考虑独立库。

## 三、数据模型（在现有表上扩展）

```sql
-- 已有：tenants(tenant_key, display_name, lifecycle_status, ...)
-- 已有：tenant_members(tenant_key, user_id, role_key, membership_status)
-- 已有：white_label_profiles(profile_id, hostname, brand...)

create table tenant_domains (
  id uuid primary key default gen_random_uuid(),
  tenant_key text not null references tenants(tenant_key),
  hostname text not null unique,
  verification_status text not null default 'pending', -- pending|verified|failed
  tls_status text not null default 'pending',
  is_primary boolean not null default false,
  created_at timestamptz not null default now()
);

-- 所有业务表加归属（示例）
alter table users add column tenant_key text not null default 'platform';
alter table orders add column tenant_key text not null default 'platform';
alter table credit_transactions add column tenant_key text not null default 'platform';
alter table product_usage_events add column tenant_key text not null default 'platform';
-- 媒体对象存储 key 前缀：tenants/<tenant_key>/...
```

隔离策略：
1. 请求进入时按 Host 解析租户 → 写入会话变量 `app.tenant_key`；
2. 业务查询一律带 `tenant_key = current_setting('app.tenant_key')`；
3. RLS 策略强制该条件，平台超管用独立角色绕过并写审计；
4. 跨租户读取必须走显式平台接口，默认拒绝。

## 四、域名与访问链路

```
客户 DNS:  app.customer.com  CNAME  ->  app.your-platform.com
平台:      验证 CNAME/TXT -> 签发证书 -> tenant_domains 标记 verified
请求:      Host = app.customer.com -> 解析 tenant_key -> 加载该租户品牌/配置
注册:      新用户写入 tenant_members(tenant_key, user_id, 'member')
计费:      订单/消耗写 tenant_key；平台按租户出账单
```

TLS 可用反向代理（Caddy/Nginx + cert-manager）或云负载均衡自动证书；应用只负责 Host→tenant 映射与验证状态。

## 五、后台产品形态

**平台控制台（你）**
- 租户列表：状态、域名、成员数、近 30 天消耗、欠费；
- 开通向导：品牌名 → 域名 → 管理员邮箱 → 套餐/额度 → 生成邀请；
- 配额与停用；代登录（审计）；
- 平台总览：租户数、收入、消耗、异常。

**租户控制台（客户）**
- 品牌与域名（仅自己的）；
- 成员与角色（邀请/停用）；
- 用量与账单（只读自己的）；
- 套餐与充值（可选）；
- 审计日志（自己的）。

## 六、实施阶段（建议）

| 阶段 | 内容 | 预估 | 风险 |
|---|---|---|---|
| P1 | 租户开通/成员/域名表 + Host 解析 + 只读租户统计 | 3–5 天 | 低（新增表/接口） |
| P2 | 业务表 `tenant_key` 回填 + 双写 + 租户过滤 | 1–2 周 | 中（触碰用户/订单） |
| P3 | RLS + 平台/租户双控制台 + 计费归属 | 1–2 周 | 高（账务） |
| P4 | TLS 自动化、配额、代登录审计、SLA | 1 周 | 中 |

**上线顺序**：P1 可先上（不影响现网）；P2 起必须在维护窗口做，先双写再切读；P3 账单必须对账演练。

## 七、当前不能对外承诺的能力

- 不能承诺“客户数据天然隔离”——业务表还没有 tenant_key；
- 不能承诺“客户独立计费”——消耗流水没有租户归属；
- 不能承诺“域名自动 HTTPS”——只有认领，没有证书闭环。

在 P1–P3 完成前，贴牌只能作为“品牌皮肤 + 单租户定制”，不要开通给第三方收费用。

## 八、验收标准（行业口径）

1. 两个租户 A/B：A 的用户无法在 B 的域名登录后看到 B 的数据（自动化越权测试）；
2. 平台超管跨租户查询必须留审计，普通管理员不能；
3. 域名验证失败/证书过期有告警；
4. 租户账单可按租户导出，和支付流水对得上；
5. 租户停用后，其域名与 API 立即拒绝，数据保留可恢复。
