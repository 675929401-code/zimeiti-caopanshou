## 四、保存/修改链路审计（关键路径）

已确认正确：
- 工作台模型配置：候选不可变、校验→预览→原子发布、数据库触发器禁止改已发布快照；
- 卡片中心：按卡版本保存，批量设置走独立 API + 每项结果；
- 智能体批量模型：按 revision CAS 更新，带审计；
- 白标草稿：`expectedRevision` 冲突检测（409）。

需要补的细节（按优先级）：
1. 白标保存成功后列表未自动刷新到最新 revision 的边界情况（需回读校验）；
2. 定时巡检调度器是单进程定时器，多实例会重复跑，需要 leader 锁；
3. 告警 Webhook 未配置，异常只落库；
4. `/api/admin/command-center` 与 `admin-command-center-domain` 已无前端引用，属死代码；
5. 生产尚未应用迁移 `20261124170000`（巡检快照/告警表 + faults 列）；
6. 巡检探测使用生产模型 Key，行业做法是独立 canary Key；
7. 429 噪声来自 `/api/cover-models`、`/api/operation-events` 高频轮询，属既有问题。

## 五、部署清单

1. 构建：`node scripts/run-build.mjs`，确认 `runningLatest=true`；
2. 迁移：按正常发布流程应用 `supabase/migrations/20261124170000_ops_patrol_snapshots.sql`（含 `notify pgrst`）；
3. 环境变量：`OPS_ALERT_WEBHOOK_URL`（可选）、`OPS_PATROL_INTERVAL_MINUTES`（默认 30）、`OPS_PATROL_SCHEDULER=0` 可关；
4. 只在一个 Web 实例启用定时巡检（避免重复探测）；
5. 部署后 45 秒检查 `ops_patrol_snapshots` 是否新增一条、`/admin?tab=dashboard` 故障清单是否渲染；
6. 回归：首页、工作台配置、带货三页签、模型与服务、智能体、发布管理；
7. 回滚：保留上一构建与数据库迁移的前向兼容（新增表/列，不删旧数据）。
