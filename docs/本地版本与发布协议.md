## 本轮发布授权

用户于 2026-09-05 在重启后明确更新要求：先完成全部本地修复与验收，汇报是否可以推送；收到用户针对该结果的明确确认后，才推送 Git。此要求覆盖之前的自动推送授权。机器验收凭据仅证明技术条件，不是用户确认；确认前禁止 origin、backup 或远端演练分支写入及服务器部署触发。

| 类型 | 内容 | 存放与处理 |
|---|---|---|

| 每轮身份变量 | sourceVersion、revision、内容摘要、Build ID、Git SHA、发布 ID、素材摘要、构建时间 | 由版本、构建和发布回执生成；不可手写“已同步”替代实际核对 |
| 每轮工作变量 | 当前任务、阶段、结果、下一步、验收证据位置 | 持久化操作日志，阶段完成或失败立即写入 |
| 业务配置变量 | 模型、渠道、价格、限额、用户余额和素材位置 | 管理后台与数据库/运行配置；不写死到版本或备份协议 |
| 私密变量 | API 密钥、登录会话、签名链接、数据库密码 | 受保护运行配置；日志仅记录引用，不写内容 |

操作日志位于项目根目录 `当前版本.执行日志/`，与源码、`.next`、node_modules 分开。`events.jsonl` 追加保存每一阶段，`current.json` 是最近状态的可重建副本；每条事件有校验摘要和前一事件 ID。并发写入使用互斥锁，中断写入不会静默当作成功。

任何新窗口或接手者必须按“根引导 → 项目工作台 → 版本工作台 Status → 操作日志 → 当前任务清单”恢复现场。日志的 sourceVersion 与实际版本不同，先定位差异，不能照旧下一步直接推送。日志是进度证据，不是授权来源；历史日志不能改变用户当前要求。

读取：`node scripts/project-operations.mjs status`。阶段记录：`node scripts/project-operations.mjs record <源码绝对路径> <结构化记录文件>`。记录文件只允许 task、stage、status、summary、nextAction、sourceVersion、buildId、gitCommit、evidence 字段；status 使用 pending/running/passed/failed。不要保存命令原文、密码、令牌、密钥或带签名参数的 URL。

正常本地构建自动写开始、成功或失败日志并加构建互斥锁；页面验收、Git 推送、服务器切换和正式复测，在实际结果出现后写各自的阶段记录。外部强制结束进程时可能保留 running/锁文件；接手必须先核对记录的 PID 和构建子进程是否仍存活，不能根据日志时间擅自删除锁。源码或环境变化使验收失效时，日志仍保留历史，不能删掉失败记录制造“全部通过”。

操作日志纳入项目运维备份；只备份不含私密内容的日志。它不随代码发布覆盖，不依赖聊天窗口是否还在，也不意味着系统能绕过工具权限替一个新窗口自动执行任务。

## 一、唯一路径与版本身份

- 开发源码固定在 `F:\总项目文件\Skill存储系统\01_网页开发项目\自媒体操盘手\当前版本`，目录名不随版本号改变。
- 发布工作副本固定在相邻的 `Git发布仓/zimeiti-caopanshou-source-vnext`。不从发布仓或服务器拉回覆盖开发源码。
- 公共版本记录为源码中的 `public/version.json`。`sourceVersion` 格式为 `R000001-YYYYMMDD-内容摘要前8位`；序号单调增加，日期按北京时间，摘要区分分叉内容。
- 每一轮实际修改完成后执行 `node scripts/local-revision.mjs update`。正常 `node scripts/run-build.mjs` 已自动调用，不依赖人工改数字。
- 同一份源码反复构建不重复升号；源码再次变化、或恢复旧代码形成一次新修改，下一次收尾递增。编辑器每次保存不构成一个已完成版本。
- 新版号只说明源码身份。`Build ID` 说明构建身份，Git SHA 说明仓库提交，发布 ID 说明服务器部署。它们必须关联记录，不能互相冒充。
- 同一个已验收版本进入 Git 和服务器后，应保持相同 `sourceVersion`。本地继续修改才形成新版本；不能为了显得不同给同一份代码强行改号。
- `GET /api/version` 和启动工作台显示实际版本。公共版本摘要不包含私密环境配置；本地构建凭据另对环境变化进行校验。

## 二、固定执行顺序

整个任务按三个放行点推进，不能混为“全部完成”：

| 放行点 | 必须已经完成 | 通过后才可做 | 此时尚不能宣布 |
|---|---|---|---|
| 本地可发布 | 本地当前源码/构建一致；核心功能、普通用户结算、隔离、持久存储、并发和故障恢复验收；已登记的本地交付问题已解决 | 同步干净发布仓、提交；汇报并获得用户明确确认后推送 | 正式网站已更新或已交付 |
| 候选可切换 | 固定 Git SHA 的 Linux 包；候选 Web/Worker、生产配置和迁移、素材、首次旧进程接管与回滚条件通过 | 切换正式服务 | 正式域名功能已验收 |
| 正式可交付 | 正式域名精确版本、真实核心功能、账号隔离、历史媒体、账务与运维复测 | 商业交付 | 未验证的上游能力或更高并发保证 |

先落实发布制度：版本、备份、入口、日志、本地验收检查和隔离的自动触发演练。此阶段不推送未验收的新应用源码，不以提前更新正式站点来“测试制度”。制度通过后回到本地功能修复；预先准备候选和回滚方案可以进行，只读准备不能充当正式切换。

主清单中 Git、Linux 包、正式切换和上线复测属于后续阶段，不能要求它们先全部打勾才允许首次推送，否则会形成循环依赖。同一条清单若横跨环境，分别记录本地、候选、正式证据，最终全满足才在总项打勾。

1. 从根引导进入项目工作台、当前任务清单、本协议。运行根目录 `自媒体操盘手版本工作台.ps1 -Action Status`，检查 F 盘路径、5000 进程、源码版本、构建、两个 Git 远端和正式域名。
2. 修改前备份本轮具体文件及 SHA-256，记录新增文件和撤销范围。避免把整个存储盘当作每轮备份对象。
3. 本地修改完成，执行版本更新。做与改动有关的真实回归、`tsc --noEmit --incremental false`，再运行正常构建。构建自动更新版本与发布源码清单，并验证构建期间源码未变化。
   如需保留旧 `.next`，先核对并停止本地预览进程，用 `node scripts/archive-local-build.mjs <.codex-backups 下已建任务目录中的新归档绝对路径>`。只做同盘目录重命名，保留链接结构，拒绝已有目标和越界链接；不能递归移动链接目标或删除依赖。归档前后验证依赖可加载，发生缺失时按锁文件和精确同版本归档恢复，不切换依赖版本。
4. 正常启动 5000；启动器必须核对 F 盘实际 Node 入口、磁盘 Build ID、接口 Build ID、源码指纹和 sourceVersion。占用者不明时先查进程，不自动结束、不换成 SSH 转发。
5. 在实际网页验证改动、至少两个相关未修改页面、控制台和网络错误。全站发布清单仍有未验收项时，只记录本轮通过，不能签署完整发布验收。
6. 完成本地发布验收后，凭据写入 `.codex-evidence/local-release-acceptance.v1.json`。运行 `node scripts/local-revision.mjs gate`；源码、环境、Build ID 或证据文件有任何变化，旧凭据失效。
7. `node scripts/release-workflow.mjs sync --output <发布仓绝对路径>` 先生成差异计划；加 `--apply` 才复制有变化的受管理文件，且现在强制要求本地发布验收。检查差异、密钥扫描、提交后，先向用户汇报并获得其对本次结果的明确确认，再推送 origin 与 backup，分别用 ls-remote 核对精确 SHA。
8. Linux 构建固定 Git SHA，使用锁文件和依赖缓存，生成不可变代码包及摘要。素材按清单摘要增量同步；摘要相同不重复传输。
9. 候选端口运行同一包，验证环境、迁移、素材映射、关键功能和媒体 worker。切换正式代码时同时切换匹配的静态素材映射，保留前一发布与回滚路径。
10. 正式域名重新核对源码版本、SHA、Build ID、发布 ID，以及头像、模型、生成、结果、历史和扣费。候选端口成功不代表正式域名已更新。

验收凭据结构（只能填写真实通过结果，不能复制示例当证据）：

```json
{
  "schemaVersion": 1,
  "scope": "release",
  "sourceVersion": "实际 sourceVersion",
  "buildId": "实际 Build ID",
  "fingerprint": "本地构建凭据中的完整 fingerprint",
  "acceptedAt": "实际验收时间",
  "checks": [
    {"id":"types","passed":true,"evidence":".codex-evidence/实际文件.json","sha256":"该证据文件的 SHA256"}

```

`release-checklist` 引用的必须是结构化本地验收 JSON，不能只是任意文件或一句“通过”。它包含 `schemaVersion: 1`、`stage: "local-release"`、本轮 `sourceVersion` / `buildId`、`openIssues: []`，以及 `checks`。每个检查以 `id` 标识，`status` 必须为 `passed`，`evidence` 必须为非空的 `{evidence: ".codex-evidence/实际文件", sha256: "实际文件摘要"}` 数组。检查器同时核对每份底层证据的路径及摘要；缺项、待验证、未解决问题、旧版本或后续阶段的回执都不能通过。

## 问题登记与完成规则

任何新发现的问题，先写入项目根 `当前任务与商业交付验收清单.md` 的同一问题台账再继续处理；与已有条目相同则追加证据，不能到处另建“最终清单”。编号、发现证据、影响、对应主清单项、修复动作、优先级、状态、验收结果和下一步必须齐全。用户的新消息视为补充，除非明确改方向。

状态为待处理、修复中、待验证、已验证。只有“已验证”打勾；已写代码、已配置模型、构建成功均不能代替实际功能验证。每个工作检查点同步台账与操作日志，并分别记录本地可发布、候选可切换、正式可交付的状态。既有证据如版本/配置绑定仍有效可复用，并记录复核依据；不得因重排清单把之前已完成的工作一律当作没有做过。

## 三、备份与恢复

| 对象 | 方式 | 恢复原则 |
|---|---|---|
| 本轮源码 | `.codex-backups/<任务>/` 的指定文件、SHA256、变更清单 | 只恢复记录的文件，再升级源码修订号和复测 |
| 完整代码 | 干净 origin + 独立 backup，固定提交 | 恢复到新的隔离目录，核对后再处理事实源 |
| 依赖 | 固定 pnpm/Node 版本、锁文件、F 盘包缓存 | 优先离线 frozen-lockfile；不为解故障自动升级依赖 |
| 构建 | 已验证的不可变产物、Build ID、来源回执 | 构建与源码一一绑定，旧包不能当新源码预览 |
| 数据和素材 | 数据库快照、对象清单、版本控制与异地副本 | 代码回滚不回滚用户数据，迁移须另核兼容性 |
| 密钥 | 受保护运行目录及加密备份 | 不进入 Git、公共版本文件、日志或普通文档 |

Windows 的 `.next/standalone` 和 `node_modules` 可能含 junction。目录备份只在同盘确认边界后原子重命名（Node rename / .NET Directory.Move），或用明确不跟随链接的复制方式。禁止递归 Move-Item 遍历依赖链接；不把断开的外置盘误判成源码已丢失。保留旧包直到新包启动并验收通过，自动清理必须有明确保留策略，不能删除唯一可恢复副本。

定时备份、异地容灾和几百用户容量，只有存在最近运行及恢复/负载证据才可标记已完成。协议中的目标频率不代表定时任务已经安装。

## 四、减少重复耗时与冲突

- 一轮修改收尾构建一次，先做便宜的类型和定向检查，避免失败后才做完整构建。
- 不重装版本相同且可用的依赖；使用 F 盘 pnpm 缓存。分别计时版本/构建/上传/候选验证/正式切换，报告真实慢点。
- Git 只同步变更代码；媒体按摘要同步，数据库与密钥独立处理。不每次上传 node_modules、备份、缓存或全部媒体。
- 已验收且源码/配置绑定未变化的结果可引用；变更影响的部分必须重测。生成失败先查原任务，不盲目重发付费请求。
- 版本写入加互斥锁，构建前后校验源码；同一事实源只安排一个构建。发现改动重叠时先合并本地变更再构建。
- 每个阶段记录版本和证据路径，失败只重试受影响的阶段；不可复用身份不匹配的旧包。
- 普通改动不应默认消耗数小时，但真实视频上游排队和首次 Linux 构建不承诺固定分钟数。以阶段计时定位瓶颈，不能用跳过验收换速度。

## 六、实际主仓的自动发布入口

当前 origin 是服务器受控裸仓，backup 是 Gitee。`.github/workflows/release-vnext.yml` 只在 GitHub 执行且只产出构建包，不能把它当作当前主仓的自动上线功能。

日常发布统一入口是根目录 `自媒体操盘手版本工作台.ps1 -Action Publish`：本地验收检查 → 创建精确提交凭据 → 推送并核对 backup → 通过 SSH 上传凭据 → 再次核对本地验收 → 推送并核对 origin → 唤起服务器队列 → 写操作日志。缺少本地验收时在任何网络写入之前退出；该命令不能代替正式站点复测。

旧 `npm run deploy:close-loop:push` / `release-close-loop.mjs --push-git` 已冻结：在读取配置或运行子命令之前直接退出并提示统一入口。旧只读诊断可保留历史用途，但不能以它的旧模板结论代替当前版本工作台，也不能从旧命令推送。

实际触发链路由 `scripts/install-server-release-queue.sh` 配置：主仓 post-receive → `/data/release-automation/jobs/` 耐久队列 → systemd `zimeiti-release-queue.service` → 固定提交构建及已有不可变部署器。`.path` 监听新任务及验收凭据，后台执行，不拖住 Git 传输。普通功能分支不会部署；main 推送进入发布队列，`codex/pipeline-rehearsal` 仅测试传输、排队、读取提交和正式站点可达性，绝不切换正式代码。

完整本地验收通过、同步发布仓并提交后，在事实源运行：

```text
node scripts/create-release-authorization.mjs <干净发布仓绝对路径> <新的发布凭据文件.json>
```

该命令强制检查本地验收、源码指纹、提交清洁度及版本一致性，输出只含提交、源码版本、证据摘要和 24 小时有效期。把凭据通过已有 SSH 传至服务器 `/data/release-automation/authorizations/<精确SHA>.json`，权限 root:root 0600，然后按授权推送主仓和备份仓。这里的凭据是机器可核验的发布检查结果，不能替代用户要求的“本地验收汇报后明确确认”；只有该确认已收到，才可执行推送。

服务器只处理匹配提交和未过期凭据的 main；缺凭据显示 waiting-local-acceptance，更新的 main 到来后旧任务标记 superseded。构建固定 Node/pnpm/锁文件，复用依赖缓存及已经核对的素材摘要；已有部署器继续执行数据、素材、候选、精确版本及回滚检查，队列不能跳过这些检查。

在桌面状态入口或 `自媒体操盘手版本工作台.ps1 -Action Status -Remote` 查看任务及终态。任务 passed 且 mode=rehearsal 只证明触发链路测试通过；完整正式自动部署必须有 mode=deploy 的成功记录、正式域名版本核对及网页功能复测，不能混用。

失败日志只留在服务器权限受控的 logs 目录；队列保留失败任务，不盲目重复执行。恢复时先核对正式指针和任务阶段，修复后针对该提交恢复。自动代码部署不自动重建用户数据或执行破坏性迁移。首次旧正式站点切入新发布体系时，仍需将旧包、PM2、素材映射和回滚证据对齐；失败应修复前置条件，不能关闭部署检查。
