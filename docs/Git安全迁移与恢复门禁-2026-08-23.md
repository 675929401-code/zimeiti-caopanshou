## 日常方向

```text
当前版本/ 本地修改
  → 本地测试与安全扫描
  → 用户当次确认
  → 当前私有 origin
  → 独立私有 backup（如已配置）
  → 全新目录恢复验证
```

日常禁止：

- 从我方 Git `pull`、`reset --hard` 或 `rsync --delete` 覆盖 `当前版本/`。
- 把第三方 upstream 直接配置为主站 origin。
- 将 `.env*`、私钥、数据库 JSON、用户上传、对象存储内容或真实模型密钥提交到代码仓。
- 使用旧 `publish-gitee-full.*`、`sync-from-git.sh`、`git-auto-deploy.sh` 或 `gitee-webhook-server.mjs` 写入、监听或覆盖当前环境；这些入口已默认拒绝执行。

## 发布/备份前必须完成

1. 轮换旧历史中可能暴露的 Gitee、服务器面板、数据库、Supabase、模型渠道和云存储凭据。
2. 对旧远端做访问日志和成员权限审计；确定保留、封存或删除策略。
3. 生成仅包含可发布源码的干净导出目录，执行 `release-preflight.mjs` 和独立密钥扫描。
4. 明确两个不同角色：`origin` 是产品主仓，`backup` 是异地代码备份仓；两者均应为私有仓并使用最小权限凭据。
5. 在全新目录 clone 指定 commit，执行 `git fsck`、依赖锁定、构建、关键页面/API 回归，再记录恢复证据。

## 灾难恢复

灾难恢复必须 clone 到新目录，例如 `恢复候选-日期-commit/`。验证通过前，不删除、不覆盖、不改名现有 `当前版本/`。恢复候选与当前版本做文件清单、配置模板、数据库迁移和静态素材对比后，由用户决定切换。

## 数据与密钥备份

- Git：只保存获准发布的源码、迁移脚本、配置模板和文档。
- 数据库：独立加密快照，记录恢复点和校验值；不得进入普通 Git。
- COS/用户媒体：对象存储版本控制或独立复制策略，保存清单和校验值。
- 密钥：密码管理器或专用 Secrets 服务，Git 仅保存变量名和获取说明。
